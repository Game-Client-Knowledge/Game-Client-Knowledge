# ECS 工程实践

## 1. 组件设计

### 1.1 保持数据职责单一

组件应围绕稳定的数据访问模式设计：

```text
推荐：
Position
Velocity
Health

谨慎：
CharacterData {
  position,
  velocity,
  health,
  inventory,
  animation,
  networkState,
  ...
}
```

过大的组件会让 System 加载无关字段，也会扩大写入冲突范围。

### 1.2 不要盲目拆成最小字段

组件也不是越小越好。经常一起访问、生命周期一致的数据可以放在一起：

```text
Transform {
  position,
  rotation,
  scale
}
```

判断依据是：

- 字段是否总被同一批 System 使用。
- 字段是否以相近频率变化。
- 字段是否共享生命周期和序列化规则。

### 1.3 避免持有不稳定内存引用

Archetype 迁移或存储扩容可能移动组件。长期保存组件指针或引用容易失效。

更稳妥的做法是：

- 保存 Entity ID。
- 在使用点重新通过 Query 或 World 获取组件。
- 只在框架明确保证有效期的作用域内保留引用。

## 2. System 设计

### 2.1 缩小读写集合

System 声明的写集合越大，可并行空间越小。

例如，把一个大系统拆成：

```text
SteeringSystem: 读取 AIIntent，写 DesiredVelocity
MovementSystem: 读取 DesiredVelocity，写 Position
```

拆分的价值是让职责和依赖更清晰。若两个步骤始终连续执行且中间数据没有复用价值，过度拆分反而会增加调度与内存成本。

### 2.2 保证遍历逻辑局部

高频 System 内应减少：

- 随机访问其他实体。
- 虚函数或动态分派。
- 每个实体单独分配内存。
- 字符串查找和哈希查询。
- 不可预测的复杂分支。

这些操作会削弱连续批处理的优势。

关于哈希表的内存布局、短哈希表的适用场景，以及分支误预测对流水线和 SIMD 的影响，参见[哈希查询与分支预测](./09-hash-and-branch-performance.md)。

### 2.3 区分纯计算与副作用

可将复杂系统分成两个阶段：

```text
并行计算阶段：读取组件，生成结果或命令
提交阶段：修改结构、发送网络消息、调用外部服务
```

这样更容易控制线程安全、重放和测试。

## 3. 性能优化顺序

建议按以下顺序优化：

1. 用性能数据确认瓶颈 System。
2. 检查 Query 是否遍历了过多实体。
3. 检查组件布局和无关数据加载。
4. 减少结构变更和随机访问。
5. 批量化昂贵操作。
6. 最后再考虑 SIMD、多线程和定制分配器。

不要在没有测量的情况下，仅凭“ECS 应该更快”做复杂优化。

### 3.1 结构变更

在 Archetype ECS 中，添加或删除组件可能复制实体的多个组件。以下模式成本较高：

```text
每帧反复 add(Active) / remove(Active)
```

可根据语义改成：

- 使用组件内部状态字段。
- 将频繁切换的实体分组处理。
- 在固定提交点批量执行结构变更。

标签是否优于布尔字段，要根据 Query 过滤收益和迁移成本判断。

### 3.2 Changed Filter

如果 System 只需处理发生变化的数据，可以记录版本号：

```text
Transform.version > RenderSyncSystem.lastRunVersion
```

Changed Filter 能减少无效工作，但会增加版本维护成本，而且“被写访问”不一定等于“值实际改变”。框架语义需要明确。

## 4. 并行执行

并行调度至少需要处理三类问题：

| 问题 | 典型方案 |
|---|---|
| 数据冲突 | 基于组件读写声明建立依赖 |
| 工作划分 | 按 Archetype、Chunk 或实体范围分片 |
| 结构变更 | 每线程 Command Buffer，结束后合并 |

并行并非总能提升性能。实体数量较少时，任务创建、同步和缓存竞争可能比计算本身更昂贵。

合理策略是为 System 或 Query 设置并行阈值，小任务直接串行执行。

## 5. 确定性与网络同步

ECS 常用于锁步、客户端预测和服务端仿真，但 ECS 本身不保证确定性。

需要额外控制：

- System 执行顺序。
- Query 遍历顺序。
- 并行归并顺序。
- 浮点计算差异。
- 随机数种子和调用次数。
- Event 与 Command 的提交顺序。

可采用：

```text
固定时间步
+ 稳定排序
+ 确定性随机数
+ 状态快照
+ 输入日志
```

如果只需要服务端权威同步，可以允许内部非确定性，再同步权威状态；无需为不必要的严格确定性支付成本。

## 6. 序列化与存档

存档不应直接复制 ECS 内部内存，因为存储布局会随版本和运行状态变化。

推荐定义稳定的数据协议：

```text
SavedEntity {
  persistentId,
  componentTypeIds,
  componentPayloads
}
```

需要考虑：

- 运行时 Entity ID 与持久化 ID 的映射。
- 组件版本升级和迁移。
- Entity 引用的重建。
- 临时组件和运行时缓存是否排除。
- 未识别组件如何兼容。

## 7. 调试与可观测性

ECS 将行为分散到多个 System 后，必须提供足够的诊断工具：

- 按 Entity 查看全部组件。
- 按 Component 或 Archetype 查看实体数量。
- 查看 System 执行顺序、耗时和读写集合。
- 记录一帧内的 Event 与 Command。
- 追踪某个组件由哪个 System 修改。
- 检查无效 Entity 引用和结构变更冲突。

一个实用的调试快照应能回答：

```text
这个实体当前有哪些组件？
它为何被某个 Query 选中或排除？
它的 Health 在哪一帧被哪个 System 改成了 0？
Dead 标签何时提交并对其他 System 可见？
```

## 8. 测试策略

### 8.1 System 单元测试

构造最小 World，只加入 System 所需组件：

```text
Given: Position(0, 0), Velocity(2, 3), deltaTime = 0.5
When: 运行 MovementSystem
Then: Position == (1, 1.5)
```

### 8.2 调度测试

验证 System 依赖和数据可见性：

```text
InputSystem 在 MovementSystem 之前执行
ApplyCommands 后 Query 才能看到新标签
存在写冲突的 System 不会并行
```

### 8.3 性质测试

对生命周期和存储层验证不变量：

```text
销毁后旧 Entity 句柄始终无效
添加再删除组件不会破坏其他组件
任意结构变更序列后 Query 结果与实际组件一致
```

## 9. 常见失败模式

| 失败模式 | 后果 | 改进方向 |
|---|---|---|
| 组件包含大量业务方法 | 数据与行为再次耦合 | 将批处理规则移到 System |
| System 任意访问整个 World | 依赖不透明，难以并行 | 声明精确 Query 和 Resource |
| 每帧大量增删组件 | 频繁存储迁移 | 批量变更或重新设计状态 |
| System 数量极端膨胀 | 调度和理解成本增加 | 按数据流合并相关步骤 |
| 所有通信都使用 Event | 状态来源难追踪 | 持续状态使用 Component |
| 长期保存组件引用 | 存储迁移后失效 | 保存 Entity 并按需查询 |
| 忽略调试工具 | 问题跨多个 System 难定位 | 建立实体、事件和修改追踪 |

## 10. 选型建议

采用 ECS 前，先回答：

1. 是否存在大量相似实体的高频更新？
2. 对象能力是否需要动态组合？
3. 当前瓶颈是否与数据布局或批量处理有关？
4. 团队能否承担调度、生命周期和调试工具建设？
5. 是否已有成熟框架满足需求？

如果前两项均为否，普通对象组合通常更简单。如果数据规模大且组件组合复杂，ECS 的收益会更明显。

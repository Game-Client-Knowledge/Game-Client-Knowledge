# C++98 基础：继承、多态、RAII、内存管理与模板

## 1. 多重继承与 mix-in 类

### 1.1 结论

多数 C++ 开发者会**完全避免多重继承，或仅以受限形式使用**。常见经验法则是：

> 只允许简单的、没有父类的类被多重继承进一个严格单继承的层级结构中。这类类有时被称为 **mix-in（混入）类**。

### 1.2 为什么避免多重继承

| 问题 | 说明 |
|---|---|
| 菱形继承 | 同一基类经两条路径出现两次，派生类持有两份副本，语义和内存都膨胀 |
| 名字二义性 | 两个基类出现同名成员时，必须显式限定 `A::x` 或 `B::x` |
| 布局复杂 | 多基类子对象的偏移计算、向下转型成本上升 |
| 虚继承的代价 | 虚基类解决菱形问题，但引入间接层，布局与构造顺序更复杂 |

虚继承可以解决菱形继承，但通常被视作"更复杂"而不是"更正确"，所以团队规范往往直接禁止普通多重继承。

### 1.3 mix-in 类的特征

mix-in 之所以允许被多重继承，是因为它天然规避上述问题：

- **无状态或轻状态**：不携带数据，或只携带与宿主无关的少量状态。
- **不参与多态**：没有虚函数或虚函数极少，不会引入复杂的虚表合并。
- **只提供一项能力**：不表达"是什么"，只表达"能做到什么"。
- **可被任何类继承**：因为无共享基类，不会产生菱形或二义性。

典型示例：日志输出能力、序列化能力、RAII 守卫（见第 3 节；引擎的 `AllocJanitor` 就是这类守卫）。

### 1.4 示例：日志能力是典型 mix-in

```cpp
// 无状态能力混入：只提供"输出日志"这一项能力
class Loggable {
public:
    void log(const char* msg) const { /* 统一日志入口 */ }
};

// 单继承主线 + 一项横向能力
class AIComponent : public Component, public Loggable {
    void tick() {
        log("AI tick");   // 混入的能力直接可用
    }
};
```

它无成员数据、无虚函数，不表达"是什么"，可以被任何类混入，且不会引入菱形或二义性。

> 引擎代码中的 `AllocJanitor`（进入作用域切换分配器、离开作用域恢复）是同一种模式，见 [引擎基础：内存分配器](../engine/01-memory-allocators.md)。

## 2. 虚函数与虚表机制

### 2.1 结论

虚函数把"调用哪个函数"从编译期推迟到运行期：通过对象内的**虚表指针（vptr）**查表，找到与实际类型匹配的函数地址。它是运行期多态的机制基础。

多态生效需要两个条件：

- 通过**基类指针或引用**调用；
- 调用的是**虚函数**。

非虚函数、或通过对象本身调用（`obj.f()`）都是编译期静态绑定。

```cpp
class Shape {
public:
    virtual double area() const { return 0; }
    virtual ~Shape() = default;          // 多态基类必须虚析构
};

class Circle : public Shape {
    double r;
public:
    Circle(double r_) : r(r_) {}
    double area() const override { return 3.14159 * r * r; }
};

Shape* s = new Circle(2.0);
s->area();     // 运行期分派到 Circle::area
delete s;      // 虚析构保证完整销毁 Circle 部分
```

### 2.2 虚表如何工作

- 含虚函数的类有一张**虚表（vtable）**：按声明顺序存虚函数地址，每个类编译期生成一份，通常放只读段。
- 每个对象有一个 **vptr**，构造时由编译器写入本类虚表地址；vptr 只出现在**含虚函数的类**里。
- `p->area()` 编译为：读 vptr → 虚表按固定下标取函数地址 → 间接调用：

```cpp
// 概念展开：p->area() 等价于
p->vptr[0](p);    // 下标 0 是第一个声明的虚函数
```

- 重写就是"在自己的虚表该下标处填自己的函数地址"；不重写则沿用基类地址。

### 2.3 代价与影响

| 影响 | 说明 |
|---|---|
| 一次间接跳转 | 比直接调用多一次内存读，通常几纳秒，可被分支预测摊平 |
| 难以内联 | 目标在编译期未知，一般不能内联（可证明具体类型时除外） |
| 对象体积 +8 字节 | 多一个 vptr，影响内存布局与缓存 |
| 二进制体积 | 每类一份虚表 |

### 2.4 为什么基类析构要 virtual

`delete 基类指针` 时若析构非虚，只会执行基类析构，派生类新增成员不析构 → 泄漏/未定义行为；虚析构才按实际类型完整销毁。反过来，**不作为基类**的类不要为了"保险"加虚析构，白白付出 vptr 与虚表代价。

## 3. RAII 与作用域守卫

### 3.1 原理

RAII（Resource Acquisition Is Initialization，资源获取即初始化）：

- **构造函数获取资源**，**析构函数释放资源**。
- 利用 C++ 局部对象在作用域结束时**必定析构**的特性，保证资源一定释放。
- 即使中途抛出异常，栈展开也会调用析构函数，因此天然异常安全。

### 3.2 朴素写法与 RAII 对比

```cpp
// 朴素写法：手动配对，异常或提前返回时漏掉 unlock
mtx.lock();
doWork();                // 若抛异常，这里漏执行 unlock
mtx.unlock();

// RAII 写法：析构必定执行
{
    std::lock_guard<std::mutex> guard(mtx);
    doWork();            // 无论正常返回还是抛异常，都会解锁
}
```

### 3.3 适用场景

| 资源类型 | RAII 类示例 |
|---|---|
| 互斥锁 | `std::lock_guard`/`std::unique_lock`（lock/unlock） |
| 文件句柄 | `std::fstream`（open/close） |
| 动态内存 | 智能指针（`unique_ptr`/`shared_ptr`） |
| 套接字/系统句柄 | 自研 `SocketGuard`（socket/close） |

核心价值是**把"必然配对"的操作交给语言机制**，而不是依赖开发者记得成对书写。

> 引擎把同一思路用于分配器上下文、GPU 状态、渲染 scope 等全局状态，见 [引擎基础：作用域守卫](../engine/02-scope-guards.md)。

## 4. 拷贝控制与三五法则

### 4.1 默认生成的成员函数

| 成员函数 | 默认行为 |
|---|---|
| 拷贝构造 | 逐成员拷贝 |
| 拷贝赋值 | 逐成员赋值 |
| 析构 | 逐成员析构 |

C++11 起还按需默认生成移动构造/移动赋值（见 [C++11 移动语义](./02-cpp11.md)）。

### 4.2 三法则 / 五法则

- **三法则（C++98）**：自定义了析构、拷贝构造、拷贝赋值中的任何一个，通常三个都要定义。因为"管理资源、深拷贝"时，默认的逐成员（浅）拷贝几乎必然错误。
- **五法则（C++11）**：涉及移动语义时再加上移动构造与移动赋值。
- 反例：类持有裸指针 `char* buf`，析构 `delete[]`；默认拷贝只复制指针值 → 两个对象析构时双重释放。

```cpp
class Buffer {                            // 三法则：深拷贝
    char* buf;
    size_t size;
public:
    Buffer(size_t n) : buf(new char[n]), size(n) {}
    ~Buffer() { delete[] buf; }
    Buffer(const Buffer& o) : Buffer(o.size) {           // 拷贝构造
        memcpy(buf, o.buf, size);
    }
    Buffer& operator=(const Buffer& o) {                 // 拷贝赋值
        if (this != &o) {
            char* t = new char[o.size];                  // 先分配，失败不破坏自身
            memcpy(t, o.buf, o.size);
            delete[] buf;
            buf = t;
            size = o.size;
        }
        return *this;
    }
};
```

要点：拷贝赋值先做**自我赋值检查**，再分配新资源，成功后才释放旧资源（保证异常安全）。

### 4.3 =delete 与 =default

- `=delete`：显式禁止某成员函数（如"不可拷贝"的类）；`=default`：显式要求编译器默认实现。
- C++98 时代的替代写法：把拷贝构造/赋值声明为 `private` 且不实现。

## 5. 内存管理基础：new/delete 与 std::allocator

### 5.1 new 表达式做了什么

```cpp
T* p = new T(args);
```

编译为三步：`operator new(sizeof(T))` 分配原始内存 → 在内存上调用 `T` 构造函数 → 返回指针。`delete p` 反之：先析构，再 `operator delete` 释放。

与 `malloc` 的对比：

| 维度 | `new`/`delete` | `malloc`/`free` |
|---|---|---|
| 构造/析构 | 自动调用 | 不调用，需手工 placement new + 显式析构 |
| 失败行为 | 抛 `std::bad_alloc`（`nothrow` 版返回 nullptr） | 返回 NULL |
| 类型安全 | 返回 `T*`，自动算大小 | 返回 `void*`，需强转、手写 sizeof |
| 重载 | 可重载 `operator new/delete` | 不可重载 |
| 关系 | 底层通常封装 `malloc` | 通用分配的基础设施 |

### 5.2 placement new：在已有内存上构造对象

不分配内存，只调用构造函数：

```cpp
void* raw = malloc(sizeof(T));   // 或对象池、对齐缓冲
T* p = new (raw) T(args);        // 在 raw 上构造
p->~T();                         // 显式析构
free(raw);                       // 或归还对象池
```

典型用途：对象池复用、序列化反序列化到指定缓冲、对齐内存上的对象构造。

### 5.3 重载 operator new/delete

- **类级重载**：只接管该类的分配，常用于统计、追踪、强制对齐。
- **全局重载**：接管所有 new，跨 DLL/so 边界需成对实现并谨慎处理版本问题。
- C++17 起提供带对齐参数的 `operator new(size_t, std::align_val_t)`，超对齐类型自动走这一版。

```cpp
struct Tracked {
    static void* operator new(size_t n) { /* 计数 + 分配 */ }
    static void operator delete(void* p) noexcept { /* 计数 - 释放 */ }
};
```

### 5.4 std::allocator 与容器

- STL 容器**不逐个 new 元素**：通过 `allocator_traits<A>` 批量申请/释放原始内存（`allocate`/`deallocate`），再在块内构造对象。
- 自定义分配器需满足 `allocator_traits` 要求的接口（含 `construct`/`destroy`），统计与策略都写在这一层。
- `vector` 扩容时通过分配器一次拿更大的块再移动/拷贝元素——分配器质量直接影响容器性能。

### 5.5 与引擎分配器的边界

C++ 层只规定**接口**：要多少字节、什么对齐、谁负责构造/析构。而"线性/栈、池、Arena、当前分配器上下文"是**策略**，属于引擎内存管理，见 [引擎基础：内存分配器](../engine/01-memory-allocators.md)。

## 6. 模板：特化与类型特征

### 6.1 为什么 numeric_limits 需要全特化

`std::numeric_limits<T>` 用**全特化**（每个具体类型一份）提供真实数值信息：

- 类型系统不表达 `int` 的范围、`double` 的 epsilon 等元数据，这些值由平台决定。
- 语言层面只提供 `sizeof`、`alignof`、类型特征等能力，没有"查询类型数值范围"的语法。
- 因此主模板给保守默认值，每个类型显式特化，标准库实现用编译器内置宏（如 `__INT_MAX__`）填充。

```cpp
template <typename T> class numeric_limits { /* 未知类型：保守默认值 */ };

template <> class numeric_limits<int>    { /* 真实值 */ };
template <> class numeric_limits<double> { /* 真实值 */ };
```

"编译器能不能自动算"：部分值可用元编程技巧计算（如无符号整型 `max = ~T(0)`），但不通用、不可靠，标准库选择显式特化保证编译期常量。

### 6.2 类型特征如何推导：is_pointer

机制是**主模板默认 false + 偏特化按形态匹配变 true**：

```cpp
// 主模板：兜底，默认不是指针
template <typename T> struct is_pointer : std::false_type {};

// 偏特化：匹配 "T*" 形态 -> true
template <typename T> struct is_pointer<T*> : std::true_type {};

// 指针自身带 const/volatile 的形态各写一份
template <typename T> struct is_pointer<T* const>          : std::true_type {};
template <typename T> struct is_pointer<T* volatile>       : std::true_type {};
template <typename T> struct is_pointer<T* const volatile> : std::true_type {};
```

匹配规则：

```text
is_pointer<int*>        -> T* 形态（T=int）       -> true
is_pointer<const int*>  -> T* 形态（T=const int） -> true
is_pointer<int* const>  -> T* const 那份           -> true
is_pointer<int>         -> 不匹配任何偏特化        -> false
is_pointer<int Obj::*>  -> 成员指针不是 T* 形态    -> false
```

- **成员指针**（`int Obj::*`）不算指针，由 `is_member_pointer` 覆盖——因为偏特化形态匹配不到。
- 现代标准库直接使用编译器内建 `__is_pointer(T)`，语义等价但编译更快、cv 组合处理更精确。
- 特化选择是**编译期纯模式匹配**，零运行时成本。

### 6.3 同类特征一览

| 特征 | 匹配形态 |
|---|---|
| `is_pointer<T>` | `T*`（及 cv 变体） |
| `is_reference<T>` | `T&`、`T&&` |
| `is_void<T>` | `void` 及 cv 变体 |
| `is_member_pointer<T>` | `T C::*` |
| `is_integral<T>` | 一组内置整型偏特化或编译器内建 |

# 项目表达与复习策略

## 1. 项目经历怎么准备

项目介绍不是功能清单。面试官更关心你面对约束时如何做判断。

每个核心项目至少准备：

```text
项目规模和个人职责
-> 最复杂的模块
-> 遇到的具体问题
-> 定位证据
-> 备选方案与取舍
-> 最终实现
-> 量化结果
-> 代价、失败或遗留问题
```

高频追问：

- 你负责的模块边界是什么？
- 最难定位的 Bug 是什么？
- 做过最有效的性能优化是什么，数据如何证明？
- 为什么选择当前架构，有哪些代价？
- 如果重新设计会改什么？
- 如何与服务端、策划、美术和测试协作？

### 1.1 一个不够好的回答

> 我负责资源加载，后来做了异步加载，加载就变快了。

问题是没有场景、瓶颈证据、个人工作、数据和代价。

### 1.2 一个更完整的回答

> 战斗切场景时主线程最长会停顿 420 ms。时间线显示同步 IO 与 Prefab 实例化
> 连续占用主线程。我把 IO、解压和可并行解析移到后台任务，将实例化按 2 ms
> 帧预算切片，并增加取消令牌处理玩家返回大厅的情况。目标机型的 P95 切场景
> 停顿降到 48 ms，代价是过渡阶段会短暂显示低精度占位资源，并增加约 80 MB
> 预取峰值。

## 2. 系统设计题

常见题目：

- 设计技能和 Buff 系统。
- 设计背包、装备和道具系统。
- 设计任务与事件系统。
- 设计 UI 框架和页面生命周期。
- 设计资源加载和卸载系统。
- 设计对象池。
- 设计战斗状态同步。
- 设计大世界场景流送。
- 设计回放或战斗复盘。
- 设计客户端日志和性能监控。

推荐回答顺序：

```text
目标与约束
-> 数据模型
-> 模块职责
-> 生命周期
-> 数据与控制流
-> 扩展性
-> 性能与并发
-> 异常和恢复
-> 测试与观测
```

不要一听“设计背包”就立刻画十七个类。先确认是否联网、谁是权威、物品规模、
是否支持堆叠与过期、失败如何回滚。没有约束的架构图通常只是线条比较多。

## 3. 按岗位安排优先级

| 岗位 | 最高优先级 |
|---|---|
| Unity 玩法客户端 | C#、Unity 生命周期、资源、UI、网络、GC |
| Unreal 玩法客户端 | C++、UObject、Gameplay Framework、反射、Replication |
| 自研引擎客户端 | C++、内存、多线程、资源、渲染、跨平台 |
| 渲染客户端 | 图形 API、GPU 管线、Shader、PBR、GPU 分析 |
| 性能优化 | CPU Cache、内存、任务系统、Profiler、GPU Bottleneck |
| 客户端架构 | 模块边界、状态管理、资源生命周期、可测试性 |

岗位描述中的名词只是起点，还应结合项目经历调整：

- 简历写了 ECS，就要准备存储、查询、调度和结构变更。
- 简历写了 Shader 优化，就要准备 GPU Capture 和前后数据。
- 简历写了网络同步，就要准备权威、预测、校正和弱网。
- 简历写了架构重构，就要准备旧方案为何失败和迁移风险。

## 4. 四阶段复习法

### 4.1 建立主干

优先掌握：

```text
一门主语言
-> 内存与并发
-> 数据结构
-> 游戏数学
-> 引擎生命周期与资源
-> 基础渲染
-> 网络同步
-> 性能分析
```

### 4.2 针对岗位

根据岗位选择 Unity、Unreal、渲染、网络或引擎专项，不要把时间平均撒给所有
词条。平均用力听起来公平，对截止日期通常不太公平。

### 4.3 项目化回答

为每类核心知识准备一个项目案例：

```text
问题是什么
-> 如何测量
-> 为什么选择该方案
-> 具体如何实现
-> 结果如何
-> 还存在哪些代价
```

### 4.4 模拟追问

对每个答案继续问：

```text
为什么？
还有别的方案吗？
这个方案什么时候失效？
数据如何证明？
线上出问题如何排查？
```

能承受连续五次“为什么”的答案，通常才算真正进入可面试状态。

## 5. 复盘记录模板

| 项目 | 记录内容 |
|---|---|
| 问题 | 原题和追问链 |
| 首次回答 | 不修饰地记录现场答案 |
| 缺口 | 定义、原理、取舍、案例或数据 |
| 修正答案 | 控制在 30 秒、2 分钟两个版本 |
| 关联项目 | 可作为证据的真实经历 |
| 下次验证 | 代码、Profiler、文档或实验 |

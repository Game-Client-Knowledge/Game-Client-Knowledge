# 作用域守卫与帧内资源管理

## 1. 为什么引擎大量使用守卫类

引擎代码大量维护"进入作用域改变全局状态、离开作用域必须恢复"的操作：

| 场景 | 进入 | 离开 |
|---|---|---|
| 分配器上下文 | Push 分配器 | Pop 分配器 |
| GPU 状态/管线 | 绑定管线、设置混合/深度状态 | 恢复上一状态 |
| 渲染 scope | 设置渲染目标、裁剪、标记 | 恢复 |
| 性能计时 | 记录开始时间 | 写入耗时并出栈 |
| 线程亲和 | 绑定线程 | 解除绑定 |

手工配对容易在早退、异常、`continue` 处遗漏，因此引擎把这些操作封装成**无状态守卫类**，把"必然配对"交给析构机制（RAII，见 [C++98 基础](../cpp/01-cpp98.md)）。

## 2. 典型实现

```cpp
class GpuScopeGuard {
public:
    explicit GpuScopeGuard(const PipelineState& state) {
        SaveAndBind(state);      // 保存旧状态并绑定新状态
    }
    ~GpuScopeGuard() {
        Restore();               // 恢复旧状态
    }
};
```

共同特征：

- **无状态或轻状态**：只持有旧状态或什么都不持有，析构即恢复。
- **可嵌套**：状态按栈保存/恢复，天然支持多层 scope。
- 命名常以 `Scope`/`Guard`/`Janitor` 结尾，如 `AllocJanitor`（见 [01-内存分配器](./01-memory-allocators.md)）。
- 编译后就是构造/析构各一次简单调用，通常可内联，零运行时抽象成本。

## 3. 帧内资源管理

- **帧分配器 + 守卫**：整段 scope 的临时数据统一从帧分配器分配，帧末 reset。
- **临时系统开关**：临时禁用物理、暂停事件广播、忽略输入等，都可用守卫表达。
- **计时与分析**：Profiler scope 守卫自动记录函数耗时并生成层级报告。

## 4. 与语言层的关系

守卫类 = mix-in（多重继承约定）+ RAII（析构必定执行）在**引擎全局状态**上的应用：语言提供机制，引擎把"切换全局状态"抽象成可嵌套的安全操作。

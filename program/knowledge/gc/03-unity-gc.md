# Unity GC：Boehm 保守式标记-清扫

## 1. 定位

Unity 的 GC 是 **Boehm–Demers–Weiser 保守式收集器（libgc）**：保守、非移动、非分代、无压缩的标记-清扫，由分配阈值驱动，支持增量标记。

最关键的一点：**两个脚本后端用的是同一个 GC**。

| 脚本后端 | 编译方式 | GC |
|---|---|---|
| Mono | C# → IL，桌面 JIT / 移动 AOT | Boehm |
| IL2CPP | C# → IL → C++ → 原生代码 | Boehm |

Mono 官方自带的 sgen（精确、分代、可压缩）**没有被 Unity 采用**。

## 2. 为什么是保守式 + 非移动

IL2CPP 把托管代码编译成 C++，意味着托管对象内存里到处是**原生代码持有的裸指针**：

1. **不能移动对象**：移动就必须更新所有指针，而 GC 无法区分"真指针"和"碰巧像指针的整数"——假指针无法被正确更新。非移动 ⇒ 无需 pinning，IL2CPP 互操作成本近乎为零。
2. **保守式是"不知道对象布局"时的最优解**：Boehm 不依赖类型元数据，直接扫内存找指针，天然适合托管/原生混合的场景。
3. **安全铁律**：宁可漏回收，绝不误回收——活对象被误删的悬垂灾难在 Boehm 里理论上不会发生。

## 3. 保守式收集器怎么工作

### 3.1 找根：纯靠"猜"

```
扫描范围：所有线程栈（含原生线程）、CPU 寄存器、全局/静态数据区、GC 自己的堆
规则：每隔一个机器字长读一个值，若值落在某已分配堆块内 → 认为是指针 → 标记该块
```

### 3.2 内部指针（Interior Pointer）

指针不必指向对象开头，指向对象中部也算数。IL2CPP 因此可以自由生成"指向数组元素/字符串中间"的引用。

### 3.3 假指针（False Pointer）：保守式的阿喀琉斯之踵

```text
某堆块地址为 0x000000001A2B3C00
数组里存了个 ulong = 0x000000001A2B3C00  —— 只是个数字
保守 GC 分不出来 → 该对象被"幽灵引用"钉住 → 本该死，死不了
```

后果是内存缓慢膨胀：大块数值数据（矩阵、浮点缓冲）越多越容易中招，排查时会在 Memory Profiler 里看到引用链指向毫不相干的数组。

## 4. 标记-清扫流程

```mermaid
flowchart LR
    A[Stop-the-world] --> B[Mark: 从根递归标记可达块]
    B --> C[Sweep: 未标记块放回空闲链表, 相邻块合并]
    C --> D[恢复线程]
```

**没有压缩阶段**，两个必然结果：

- 长期运行碎片化，堆通常只增不减；
- 分配走空闲链表（malloc 式），没有 bump 指针，比 .NET 年轻代分配慢一个量级。

## 5. 触发时机

| 触发来源 | 说明 |
|---|---|
| 分配阈值 | 空闲链表无法满足请求（最主要来源） |
| 手动调用 | `System.GC.Collect()` |
| 场景切换 | 加载场景时自动 GC，避免把卡顿带进战斗 |
| 内存压力 | 系统低内存 |
| 增量调度 | 开启增量 GC 后按帧预算持续标记 |

**GC 频率与分配速率成正比**：每帧分配越多的垃圾，回收越频繁。所以 Unity 优化的核心口号是"每帧零分配"。

## 6. 增量 GC（2019.1+）

把一次大停顿拆成多帧小停顿：

```text
不用增量: |████████████ 全部标记一次完成（一个大卡顿）|
增量:     |██| |██| |██| |██| ...  每帧只停顿几毫秒
```

- 每帧花固定时间片做标记，时间到就放行游戏线程；
- 标记期间的新引用由写屏障/脏页机制捕捉，保证不漏标；
- API：`GarbageCollector.CollectIncremental(timeSlice)`、`GarbageCollector.GCMode = Disabled`（紧急时刻禁用 GC，慎用）。

## 7. 双生命周期：托管包装器 vs 原生对象

Unity 特有的结构，理解它才能看懂内存分析：

```text
C# 侧: GameObject 对象 ──→ 只是托管堆里的"包装器"
                            │ 内部藏着指向原生对象的指针
                            ▼
C++ 侧: 引擎真正的 GameObject（网格、变换、组件数据都在这）
```

- `Destroy(go)` 销毁的是**原生对象**，托管包装器仍留在堆里等 GC 来收；
- 因此 Unity 重载了 `==`：原生部分没了之后，包装器 `== null` 返回 **true**（"假 null"）；
- **GC 统计的只有托管包装器和纯 C# 对象**；纹理、网格、音频等原生内存由引擎资源系统管理（`Resources.UnloadUnusedAssets()`），是另一套账。

## 8. 常见分配来源与对策

| 分配来源 | 对策 |
|---|---|
| 装箱（值类型塞进 object） | 泛型 |
| 每帧字符串拼接 | `StringBuilder`、缓存 |
| 闭包/委托、LINQ | 手写循环、缓存委托 |
| `GetComponents<T>()` 等返回数组的 API | `List<T>` 重载 / `NonAlloc` 版本 |
| 协程里 `new WaitForSeconds` | 缓存实例 |
| Dictionary 扩容 | 预分配容量 |

通用手段：对象池、能用结构体就不用类、组件引用缓存，以及最后的逃逸通道——`NativeArray<T>(Allocator.Temp)` 与 DOTS/ECS + Burst，完全绕开托管堆。

## 9. 根本代价总结

| 问题 | 根源 |
|---|---|
| 无分代 | 每次回收全堆扫描，成本随存活对象线性增长 |
| 无压缩 | 碎片化，堆只增不减 |
| 假指针 | 对象幽灵存活、内存膨胀、排查困难 |
| stop-the-world | 增量化后仍有每帧小停顿 |
| 分配慢 | 空闲链表分配 |
| 调优手段少 | 没有分代开关、延迟模式等 .NET 级旋钮 |

## 10. 阅读结论

1. Unity GC = 保守 + 非移动 + 非分代 + 无压缩的标记-清扫，是"给 C 用的 GC"被移植进游戏引擎。
2. 它用假指针风险、全堆扫描和碎片化，换来了 IL2CPP 架构下托管/原生指针零成本互操作。
3. 实战重心不是"调 GC"，而是让垃圾不进堆：对象池、结构体、缓存、NonAlloc API。

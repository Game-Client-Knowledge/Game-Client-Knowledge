# 协程、事件与状态机速记

## coroutine 的本质

coroutine 是同一 VM 内的**协作式执行单元**：主动 `yield` 才暂停，`resume` 后从原位置继续；默认不并行、不使用额外 CPU 核，死循环仍会卡住宿主线程。

```text
resume(co, A) -> 首次函数参数 A
yield(X)      -> resume 返回 true, X
resume(co, B) -> yield 表达式得到 B
return R      -> 最后一次 resume 返回 true, R
```

`resume` 失败返回 `false, error`，调度器必须补充 coroutine traceback。状态包括 `suspended`、`running`、`normal`、`dead`。

## 生产调度器的合同

coroutine 只保存执行现场，以下责任都属于调度器：

- 等待时间、事件、请求和资源加载；
- owner/scope 绑定与批量取消；
- 超时、错误栈、恢复值和恢复顺序；
- 每帧恢复预算与防止同帧重复恢复；
- 场景/页面销毁后的失效检查；
- 指标：活跃数、恢复数、耗时、取消、超时、错误。

**取消必须是一等能力。** 底层工作未必能中断，但取消后结果不能重新进入已关闭页面。结构化 scope 比散落的 timer/token 更可靠。

## 事件、命令与消息

| 模型 | 语义 | 关键约束 |
|---|---|---|
| 事件 | 某事已经发生，可多订阅者 | 顺序、重入、错误隔离、解绑 |
| 命令 | 请求唯一处理者执行动作 | 结果、拒绝、幂等 |
| 查询 | 请求返回数据 | 一致性、缓存与超时 |
| 消息 | 跨线程/网络传输数据 | 序列化、版本和投递线程 |

事件总线至少要定义：`on` 返回 token、owner 批量解绑、发射时增删监听的规则、回调顺序、载荷合同、异常是否阻断后续监听。购买之类的动作不应伪装成广播事件。

## 状态机与协程的选择

- **状态机**：互斥状态、显式转移、可检查/恢复；适合角色、页面和协议状态。
- **coroutine**：一次顺序流程中的多次等待；适合剧情、引导、技能表现。
- **行为树**：可组合决策；适合 AI。
- **事件**：发布事实，不承载隐式控制流。

可组合为：Combat 状态 → 行为树选动作 → coroutine 执行技能阶段 → 事件通知 UI。

状态机实现要防止 enter/exit 重入、同帧无限转移、非法目标状态和更新中销毁自身。

## 原生边界与热更新

能否在 Lua → C/C#/C++ → Lua 的嵌套调用中 yield，取决于 Lua 版本、C API continuation 和绑定框架。稳妥模型是：

```text
Lua 发请求并 yield(requestId)
-> 原生异步工作
-> 主线程结果队列
-> 调度器校验 owner/generation
-> resume(task, result)
```

挂起 coroutine 保存旧函数、局部变量、upvalue 和字节码位置。更新文件不会升级栈帧。补丁前应取消可重建任务，关键流程把进度保存在显式状态中，必要时重启脚本域。

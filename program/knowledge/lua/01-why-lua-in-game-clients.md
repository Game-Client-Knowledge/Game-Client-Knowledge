# Lua 在游戏客户端中的边界

## 30 秒回答

> Lua 是嵌入宿主进程的业务脚本层。C++/C# 负责引擎、平台能力和批量计算，Lua 负责 UI、活动、任务、技能与跨帧流程等高变化逻辑。它的核心收益是迭代速度和运行时组合能力，不是替代原生性能。边界应按变化频率、数据规模、调用密度、所有权复杂度和安全要求划分。

## 分层结论

```text
Lua：规则、流程、展示、配置消费
  -> 粗粒度命令
Bridge：类型检查、封送、句柄与错误转换
  -> 稳定窄接口
Native：渲染、物理、资源、网络、平台与批处理
```

| 更适合 Lua | 更适合原生 |
|---|---|
| UI/活动/任务/技能编排 | 渲染、物理、动画蒙皮 |
| 少量对象的高层决策 | 海量实体逐帧更新 |
| 状态机、事件、异步流程 | SIMD、连续内存、硬实时任务 |
| 可版本化的业务规则 | ABI、线程、文件与平台 API |
| 开发工具和受控配置 | 资产/战斗的安全权威判断 |

客户端 Lua 仍不可信；付费、资产和最终战斗结果必须由服务端验证。

## 嵌入与调用成本

宿主创建 `lua_State`、注册 API、安装模块 loader，再从稳定入口驱动脚本。一次 `player:setPosition(...)` 可能经历：

```text
Lua 字段查找 -> self 补入 -> wrapper
-> 参数检查/转换 -> handle 有效性验证
-> 原生调用 -> 返回值转换 -> VM 继续执行
```

所以优化优先级通常是：**减少边界次数 > 微调包装函数**。让 Lua 提交一批移动命令，优于逐实体 getter/setter。

## VM、线程与执行方式

- 标准 Lua 通常先编译为 VM 字节码再解释执行；字节码不保证跨版本、架构和构建配置兼容。
- LuaJIT 只会编译合适的热点路径；trace exit、C 边界、平台限制和 FFI 风险仍需剖析。
- coroutine 共享 VM 的全局状态和 GC，不等于独立 VM，也不会自动并行。
- 多数项目让一个 VM 固定在主线程；工作线程完成 I/O/计算后，通过队列把结果投递回脚本线程。
- 多 VM 提供隔离和线程独占，但带来模块/内存重复、消息传递、调试和更新复杂度。

## 脚本更新的边界

Lua 文件易替换，不代表热更新简单。必须同时考虑：

- `package.loaded` 之外的旧模块和缓存函数；
- 闭包 upvalue、挂起 coroutine、原生回调；
- 运行状态与资源版本迁移；
- manifest、签名、灰度、安全点、自检与回滚；
- 商店政策和平台合规。

“Lua 支持热更新”只能算开场，说明一致性与失败恢复才算完整回答。

## 高频追问

**为什么不用全 C++/C#？** 业务变化频繁，脚本可降低编译、发版和跨岗位协作成本；代价由类型检查、测试和运行时治理补上。

**为什么不用全 Lua？** 底层系统需要高吞吐、可控布局、平台 API 和严格生命周期；边界过细还会放大封送成本。

**如何决定一段逻辑下沉？** 先用目标机数据确认瓶颈，再看数据规模、边界次数和所有权；优先下沉批量内核，不机械重写全部业务。

**项目证据应讲什么？** VM/绑定版本、脚本规模、最热 Bridge API、每帧调用量、一次边界重构或泄漏治理的前后指标。

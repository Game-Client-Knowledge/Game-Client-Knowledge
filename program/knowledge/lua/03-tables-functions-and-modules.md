# Table、闭包与模块速记

## Table 的语义

Table 是“非 `nil` 键到值”的映射，可承载序列、字典、对象、集合和模块，但这些是**业务约定**，不是不同容器类型。赋值复制引用，不会深拷贝。

主流实现常有数组部分和哈希部分，这是性能实现，不是语言合同。不要据此推断 `pairs` 顺序或编写依赖布局的逻辑。

## 序列的三个陷阱

| 主题 | 结论 |
|---|---|
| `#t` | 仅对紧凑序列可靠；有空洞时只保证某个边界 |
| `ipairs` | 从 1 连续遍历，遇到第一个 `nil` 停止 |
| `pairs` | 遍历所有键，但顺序未规定 |

确定性战斗、回放、协议和序列化要维护显式顺序。若每帧都“收集 key 再排序”，应评估改成有序数组或双索引结构。

遍历时修改容器应使用：延迟变更、快照、倒序删除或待处理队列。`table.remove(t, 1)` 是 O(n)，队列应用 head/tail；无序数组可在业务允许时 swap-remove。

## 函数、闭包与 upvalue

函数是一等值，适合策略表、命令分派和回调。闭包捕获的是外部变量关联，不只是创建瞬间的值。

典型泄漏链：

```text
全局 EventBus / Timer / Registry
  -> callback closure
  -> upvalue self
  -> Panel / Scene / native wrappers
```

GC 不会回收仍可达对象。解决方案是 owner scope、订阅 token、批量解绑和可观测的 listener/task 计数。循环中创建回调时显式捕获当前迭代局部值，避免版本和写法差异。

## 模块与 `require`

推荐模块：私有实现使用 `local`，文件返回公开 Table。`require(name)` 的概念流程：

```text
查 package.loaded
-> searcher/loader 查找模块
-> 执行 chunk
-> 缓存返回值
-> 返回模块对象
```

面试要点：

- 同名模块通常只执行一次；
- 模块名如何映射资源由 searcher 和宿主 loader 决定；
- 清空 `package.loaded` 只影响未来 `require`，不会更新旧引用；
- 循环依赖常暴露边界不清，应抽公共依赖、注入接口或拆分定义/初始化；
- `load/dofile` 执行动态代码，不能直接接受不可信输入。

## 数据合同

Lua 配置“能执行”不等于“数据正确”。构建期应校验 schema、类型、范围、重复 ID、引用完整性和版本；生产包加载已验证数据。

浅拷贝只复制第一层。深拷贝必须定义循环引用、共享子图、元表、function/userdata/thread 与弱表如何处理。只读代理只能约束普通访问，不能作为安全边界。

## 性能边界

- 连续列表、ID 字典、集合、队列应使用不同形态，不让一个 Table 承担全部语义。
- 热路径关注临时 Table、rehash、头部插删和多层查找，但先用 profiler 证明。
- 标准 Lua 没有可移植的 `table.reserve`；实现专属预分配应封装在适配层。
- 配置或对象池长期持有 Table 时，要定义清理旧字段和借用期限。

## 高频追问

**Table 是数组还是哈希表？** 语义上是映射；连续整数键形成序列约定，实现可用数组/哈希混合优化。

**为什么 `#t` 可能不等于元素数？** 空洞 Table 的长度定义不是计数，也不是最大整数键。

**为什么闭包会泄漏？** 根对象保留闭包，闭包通过 upvalue 保留业务对象图。

**如何保证遍历确定性？** 维护显式顺序，不依赖 `pairs`；随机数、原生返回顺序也纳入同一合同。

**如何证明模块边界合理？** 展示依赖方向、循环依赖治理、测试替身以及热更时模块身份和状态策略。

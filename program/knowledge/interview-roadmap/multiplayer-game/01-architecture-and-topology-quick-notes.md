# 多人游戏架构、权威与拓扑速记

## 四种常见拓扑

| 拓扑 | 核心 | 优点 | 主要代价 |
|---|---|---|---|
| Dedicated Server | 独立进程维护权威对局 | 公平、稳定、易审计 | 成本、部署、跨区延迟 |
| Listen Server | 一名玩家兼任服务器 | 成本低、适合合作游戏 | 房主优势、作弊、退出迁移 |
| P2P | 玩家直接交换数据 | 路径短、基础设施少 | NAT、安全、分歧、暴露地址 |
| Relay | 中继负责转发 | 简化连通性、隐藏地址 | 中继成本；不自动拥有权威 |

拓扑与同步模型正交。Dedicated Server 可以转发帧输入；P2P 可以交换状态；Relay 也可以配合权威后端。

## 权威模型

- **服务器权威**：客户端提交输入/请求，服务器决定关键结果。
- **房主权威**：Listen Server 的房主裁决，其他玩家信任房主。
- **对等协商**：各节点执行模拟，通过输入、Hash 或共识发现分歧。
- **混合权威**：服务器裁决战斗/资产，客户端拥有摄像机、表现和局部预测。

客户端拥有表现权和预测权，不代表拥有最终状态权。

## 服务职责

```text
Gateway：连接、认证、限流、路由
Presence/Social：在线状态、好友、组队
Lobby/Matchmaking：房间、条件、匹配
Allocator：区域、机房、实例和容量选择
Game Server：权威模拟、同步和对局生命周期
Result/Rank：结算、排名、奖励和幂等
Replay/Observe：回放、观战、重连检查点
```

早期项目可以合并部署，但代码边界和数据所有权仍应清楚。

## 房间、实例、分区与大世界

| 模型 | 适用 |
|---|---|
| Room/Match Instance | FPS、MOBA、格斗等独立对局 |
| Dungeon Instance | MMO 副本，按队伍动态创建 |
| Zone/Shard | 大世界按区域或玩家群拆分 |
| Seamless World | 多区域流送与跨服迁移 |

跨区迁移要处理：

- 玩家权威状态冻结与快照；
- 目标服务器预留容量；
- Session/Entity ID 连续性；
- 未完成交易和网络请求；
- 客户端资源与连接切换；
- 失败回滚和重复迁移幂等。

## 服务器分配

Allocator 选择：

- 地域和 RTT；
- 游戏版本、模式和平台；
- 房间容量与 CPU/内存水位；
- 专用硬件/反作弊要求；
- 队伍成员的延迟公平；
- 成本和故障域。

只按“剩余人数槽位”分配可能把重负载房间继续压在同一台机器上。应使用 Tick Time、CPU、内存、带宽和实例启动时间。

## 权威游戏服务器主循环

```text
接收输入 -> 按 Tick 排序/验证
-> 玩法、物理和 AI
-> 生成权威状态与事件
-> AOI/优先级/压缩
-> 发送快照或输入帧
-> 记录回放、指标和结算证据
```

网络线程不直接并发修改世界。常见做法是将已解析消息放入 Tick 边界队列，再由模拟线程消费。

## Listen Server 与房主迁移

房主离开时：

1. 选择新房主；
2. 确认共同认可的状态或检查点；
3. 迁移房间密钥、成员和 Tick；
4. 客户端重连新主机；
5. 防止旧房主继续发送有效消息；
6. 处理迁移失败和分裂房间。

如果房主拥有未验证的完整权威，迁移无法修复之前已经发生的作弊。

## 高可用与故障

- 无状态 Gateway 可水平扩展；
- Lobby/Matchmaking 状态需要幂等和持久化；
- Game Server 常以房间为故障单元；
- 对局服崩溃可从输入日志/检查点恢复，或按政策判定无效；
- 结算采用唯一 Match ID，避免重试重复发奖；
- 区域故障需要停止新分配并迁移等待队列；
- 心跳只证明进程活着，不证明 Tick 正常。

## 容量估算

```text
单实例容量
= CPU Tick 预算
+ 常驻/峰值内存
+ 上下行带宽
+ 玩家与实体上限
+ 最坏技能/AI/物理场景
```

使用机器人、回放输入和最坏内容做压测，不能只用空房间连接数。

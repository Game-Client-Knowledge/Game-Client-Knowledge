# 确定性帧同步

## 核心结论

帧同步通常同步的是**导致状态变化的输入或命令**，而不是持续同步每个实体的位置。所有参与模拟的节点从相同初始状态出发，以相同 Tick、相同输入和相同规则运行，得到相同结果。

```text
客户端输入 -> 服务器收集/验证/排序
-> 广播 Tick N 的完整输入集合
-> 所有模拟节点执行 Tick N
-> 得到相同世界状态
```

这里的“帧”是逻辑 Tick，不是渲染帧。

## 同步什么

常见输入帧：

```text
InputFrame {
  matchId
  simulationTick
  commands[] {
    playerId
    inputSequence
    commandType
    targetId / targetPoint / parameters
  }
  previousStateHash?
}
```

RTS 中可能同步“单位 1001 移动到格子 X”；格斗中可能同步方向键与攻击按钮；棋类同步落子命令。

不持续下发位置并不等于永不发送状态。服务器仍可能发送：

- 开局初始状态；
- 周期性状态 Hash；
- 中途加入/断线重连检查点；
- 分歧后的纠正快照；
- 观战快照；
- 反作弊审计数据。

## 客户端职责

1. 在本地 Tick 采集并编码输入；
2. 将输入发给服务器，必要时冗余最近输入；
3. 按服务器确认的顺序执行完整输入帧；
4. 使用同版本数据和确定性模拟；
5. 周期性计算状态 Hash；
6. 缓存输入日志，用于追帧、回放和重连；
7. 将逻辑模拟与非确定性表现分开。

传统 Lockstep 客户端通常等待 Tick 的完整输入集合，因此不需要像状态同步那样对权威位置做 Reconciliation，但会引入输入延迟。

## 服务器职责

最小服务器可以只做：

- 收集每个玩家某 Tick 的输入；
- 校验输入频率、权限和参数；
- 确定输入顺序和迟到策略；
- 广播完整输入帧；
- 管理超时、掉线、重连和观战。

更安全的服务器会同时运行同一套模拟：

- 验证状态 Hash；
- 判断输入在当前状态是否合法；
- 隐藏战争迷雾等敏感信息；
- 对分歧节点下发检查点或踢出；
- 生成权威回放和结算。

因此“帧同步天然防作弊差”不准确。安全性取决于服务器是否验证输入、是否拥有权威模拟，以及客户端获得了多少不该看到的信息。

## Tick 推进策略

### 严格等待

Tick N 的所有输入到齐才推进。

优点：逻辑简单，不需要回滚。

缺点：最慢玩家决定所有人的响应，抖动会直接卡住模拟。

### 固定输入延迟

本地在 Tick N 产生输入，安排到 `N + D` 执行，给网络留出 D 个 Tick。

优点：降低迟到概率，节奏稳定。

缺点：本地操作也会固定延迟。

### 超时填充

输入未到时使用 No-op、沿用方向或游戏定义默认命令。

优点：不会永久阻塞。

缺点：迟到真实输入必须丢弃、纠正或进入 Rollback，策略会影响公平性。

## 确定性要求

满足“同输入”只是第一步，还要保证执行结果一致：

- 固定 Tick 和固定更新顺序；
- 稳定遍历顺序，不能依赖 Hash 容器实现顺序；
- 固定随机种子和随机数调用顺序；
- 避免读取墙钟、线程完成顺序和设备状态；
- 明确整数溢出、舍入和定点数规则；
- 避免平台差异明显的浮点、物理和三角函数，或使用确定性实现；
- 数据表、脚本、地图和逻辑版本完全一致；
- 并行系统的归并顺序确定；
- 禁止 GC/finalizer 等时机影响游戏语义。

确定性不是“尽量一样”，而是能通过同一输入日志稳定重放并得到同一 Hash。

## 状态校验与分歧定位

不要只对整个世界做一个 Hash，然后在不一致时束手无策。可分层：

```text
World Hash
  -> System Hash：Movement / Combat / Economy
  -> Entity Chunk Hash
  -> 关键字段差异
```

每隔若干 Tick 上报 Hash；发现分歧时保存输入窗口、逻辑版本和最早分歧 Tick。调试目标是找到**第一个不同的写入**，不是最后画面不同的位置。

## 重连与中途加入

只重放整场输入在长局中成本过高。常用方案：

```text
Checkpoint at Tick K
+ K+1 到当前 Tick 的输入日志
-> 客户端高速追帧
-> 追上后恢复正常显示
```

检查点必须包含所有会影响未来模拟的状态，包括 RNG、定时器、实体 generation 和系统内部队列。

## 适用场景

适合：

- RTS 和棋类；
- 玩家输入量小、世界状态量大的模拟；
- 需要回放、观战和确定性验证的战斗；
- 能控制全部平台逻辑与数据版本的项目。

不适合或代价较高：

- 强依赖非确定性物理的大世界；
- 大量中途加入且检查点昂贵；
- 需要隐藏全局信息但客户端必须完整模拟；
- 跨平台浮点与第三方系统难以保证确定性；
- 任一慢节点都可能拖累严格 Lockstep。

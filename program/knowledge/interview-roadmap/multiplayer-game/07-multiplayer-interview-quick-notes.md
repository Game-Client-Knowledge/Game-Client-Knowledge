# 多人游戏面试冲刺

## 一分钟主回答

> 多人游戏从认证、组队和匹配开始，由分配服务选择区域和游戏服务器。游戏服务器通常维护权威世界，客户端发送输入并通过预测立即表现；远端对象使用快照插值，服务器再按状态同步、确定性帧同步或 Rollback 传播结果或输入。协议按业务拆分可靠性，使用 Tick、Sequence、ACK、幂等和版本处理丢包、乱序与重试。大规模场景通过 AOI、优先级、Dormancy、Delta 和量化控制带宽，掉线通过快照或检查点恢复。最后要用网络模拟、回放、分层 Hash、Tick Trace 和业务指标验证，并通过服务器校验与风控保证公平。

## 高频题速答

| 问题 | 回答抓手 |
|---|---|
| Dedicated 与 Listen Server？ | 独立权威更公平稳定；房主服便宜但有房主优势和迁移问题 |
| P2P 与 Relay？ | P2P 直连；Relay 转发、隐藏地址和解决连通性，不自动裁决 |
| 状态同步与帧同步？ | 前者同步结果，后者同步按 Tick 排序的输入 |
| Rollback？ | 预测缺失输入，真实输入不同时恢复历史并重模拟 |
| 本地预测？ | 客户端先执行输入，服务器状态到达后恢复并重放未确认输入 |
| 远端插值？ | 故意落后服务器，在两个历史快照之间显示 |
| TCP 与 UDP？ | 先看业务可靠性和延迟语义，不由同步模型直接决定 |
| AOI？ | 每连接只复制相关实体，兼顾带宽、CPU 和隐藏信息 |
| Delta？ | 相对客户端已确认 Baseline 发送变化 |
| 重连？ | 状态同步取快照；帧同步/Rollback 用检查点 + 输入历史追帧 |
| 防作弊？ | 客户端提交意图，服务器权威验证；完整性和行为检测作为补充 |
| Matchmaking？ | 平衡 MMR、RTT、队伍、平台、风险和等待时间 |

## 设计题：100 人大逃杀

回答主线：

```text
Dedicated Server 权威
-> 区域和队伍匹配，预热实例
-> 玩家移动使用状态同步 + 预测
-> 远端快照插值
-> Replication Graph / Spatial AOI
-> 按距离、威胁和事件分层频率
-> Hitscan 使用有限 Lag Compensation
-> 掉线保留槽位并下发区域快照
-> 服务器校验移动、射击和资源
-> 监控 Tick、带宽、校正和 AOI 实体数
```

需要说明最坏场景：决赛圈玩家集中、烟雾/投射物、批量观战和服务器 Tick 尖峰。

## 设计题：RTS

```text
低频玩家命令
-> 服务器验证并按 Tick 排序
-> 各端确定性模拟
-> 固定随机、顺序和数值
-> 周期状态 Hash
-> Checkpoint + Input Log 支持重连/观战
-> 战争迷雾最小化下发
-> 服务器可同步运行权威模拟
```

不能只说“帧同步带宽低”，还要回答确定性、追帧、隐藏信息和慢玩家处理。

## 设计题：匹配系统

先澄清：

- 单排/组排；
- 玩家规模和地区；
- MMR 模型；
- 模式、角色和平台；
- 最大等待时间；
- 是否允许机器人、跨区和 Backfill。

再设计：

```text
Queue Ticket
-> 按 Region/Mode/Party 分桶
-> Skill/RTT 多目标评分
-> 随等待时间扩大范围
-> Reservation + Server Allocation
-> Accept/Ready/Connect
-> 失败重排或 Backfill
```

验证 Queue P95、预测胜率、实际质量、跨区比例和连接失败率。

## 设计题：断线重连

1. 检测连接断开，进入 Grace Period；
2. 保留玩家 Slot 和权威实体；
3. 客户端重新认证并获取 Match Token；
4. 校验 Match、账号和版本；
5. 状态同步下发 Keyframe，帧同步下发 Checkpoint + 输入；
6. 补齐可靠事件；
7. 恢复控制，不重复 Spawn、扣费或发奖；
8. 超时后按模式交给 AI、Backfill 或结束。

## 设计题：跨区大世界

- Zone 拥有局部实体权威；
- Global ID + Generation/Epoch；
- 边界预加载目标 Zone；
- 迁移事务冻结、快照、接管和确认；
- 客户端连接/资源平滑切换；
- 附近实体兴趣集合重建；
- 失败回滚；
- 跨 Zone 交易和战斗有唯一所有者。

## 常见错误

| 错误说法 | 问题 |
|---|---|
| “多人游戏就是客户端发位置” | 忽略权威、输入、校验和时间线 |
| “UDP 快，所以全部 UDP” | 忽略可靠性、拥塞和业务幂等 |
| “P2P 不需要服务器” | 仍可能需要认证、匹配、Relay、结算和风控 |
| “快照 20 Hz 就只能 20 FPS” | 渲染可预测和插值 |
| “帧同步绝不传状态” | 检查点、Hash、重连和纠正仍需要状态 |
| “可靠包不会丢业务” | 重试、重复、顺序和服务重启仍需幂等 |
| “房间满 100 人就是容量 100” | 还要验证实体、技能、Tick、内存和带宽 |
| “Ping 低体验就好” | 服务器 Tick、Jitter、缓冲和渲染也影响延迟 |

## 回答模板

```text
结论：选择什么拓扑、权威和同步模型
-> 数据流：客户端上行、服务器模拟、下行内容
-> 时间：Tick、预测、插值和校正
-> 协议：可靠性、Sequence、版本和幂等
-> 规模：玩家/实体/带宽/服务器容量
-> 失败：掉线、迁移、服崩和重复结算
-> 安全：最小信息和服务器验证
-> 验证：弱网、回放、压测和线上指标
```

## 项目证据

准备：

- 玩家/实体上限、Server Tick 和发送频率；
- 单连接带宽 P50/P95；
- RTT/Jitter/Loss 测试档位；
- 校正距离、Snapshot 欠载和 Rollback 深度；
- 匹配 Queue P95 与连接成功率；
- 重连耗时和成功率；
- 单实例 CPU/内存/带宽；
- 一次不同步、重复结算或服务器卡顿的完整排查。

## 最终自测

- [ ] 能画出认证到结算的完整链路。
- [ ] 能区分拓扑、权威、传输和同步模型。
- [ ] 能解释自己与远端对象为何使用不同表现策略。
- [ ] 能设计 AOI、优先级和带宽预算。
- [ ] 能说明状态同步与帧同步的重连差异。
- [ ] 能给出服务器崩溃、房主迁移和重复结算方案。
- [ ] 能用指标而不是“感觉流畅”证明设计。

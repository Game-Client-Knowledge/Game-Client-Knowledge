# 权威、时间轴与网络语义

## 权威先于同步

同步方案首先要回答“发生冲突时相信谁”。

| 权威模型 | 最终裁决者 | 优点 | 风险 |
|---|---|---|---|
| Dedicated Server | 独立服务器 | 安全、稳定、易统一版本 | 服务器成本和往返延迟 |
| Listen Server | 房主客户端兼服务器 | 部署便宜 | 房主优势、迁移和作弊风险 |
| P2P | 对等节点共同推进 | 低基础设施成本、路径可能更短 | NAT、作弊、分歧与断线处理复杂 |
| Relay | 中继只转发或有限验证 | 隐藏地址、简化连通性 | 不等于权威模拟 |

拓扑不决定同步模型。Dedicated Server 可以转发帧输入，P2P 也可以交换状态。

客户端通常拥有的是**表现权和预测权**，不是最终状态权：

- 可以立即播放开火动画；
- 可以预测角色移动；
- 不能自行决定弹药未消耗、伤害必定生效或付费成功；
- 服务器确认后，客户端要接受校正或回滚。

## 三条时间线

网络游戏至少同时存在：

```text
Simulation Time：固定 Tick 推进规则与物理
Server Time：服务器权威时间轴
Render Time：客户端用于平滑显示的延迟时间轴
```

墙钟时间不能直接作为模拟依据。系统时钟会跳变，应使用单调时钟测量间隔；模拟使用整数 Tick 或固定步。

常见关系：

```text
Server 正在模拟 Tick 1000
客户端已预测到 Tick 1002
客户端远端表现停留在 Tick 994~996 之间做插值
```

本地玩家可以走在服务器确认之前；远端对象通常故意落后一个插值缓冲，以换取连续的两个快照。

## Tick、序列号与确认号

不要让一个字段承担所有顺序语义：

| 字段 | 解决的问题 |
|---|---|
| `simulationTick` | 这条输入/状态属于哪个逻辑步 |
| `packetSequence` | 网络包的新旧、丢失和乱序 |
| `inputSequence` | 本地输入的顺序与服务器确认 |
| `snapshotSequence` | 快照顺序和增量基线 |
| `ack` / `ackBits` | 哪些包或消息已经收到 |
| `entityGeneration` | ID 重用后区分新旧实体 |

Packet Sequence 不能代替 Simulation Tick：一个包可以携带多个 Tick，也可能重传旧 Tick。

## 延迟、抖动、丢包与乱序

- **Latency/RTT**：决定输入到确认的等待时间。
- **Jitter**：到达间隔不稳定，插值缓冲和自适应延迟主要应对它。
- **Packet Loss**：需要容错、冗余、重传或后续状态覆盖。
- **Reordering**：必须通过序列号丢弃旧数据或重新排序。
- **Duplication**：事件和命令要幂等或去重。

不要对所有数据都使用可靠有序传输：

- 最新位置可覆盖旧位置，旧包重传价值低；
- 登录结果、生成实体、结算和背包变化通常要求可靠；
- 高频状态如果与可靠事件共用一个严格有序队列，丢一个包可能造成队头阻塞。

## 同步频率不等于渲染频率

一个常见配置可能是：

```text
客户端渲染：120 Hz
服务器模拟：60 Tick/s
状态快照：20 Hz
输入发送：30~60 Hz
低频属性：1~5 Hz 或变化时发送
```

客户端通过预测和插值填补频率差。把所有状态按渲染帧发送通常既浪费带宽，也无法消除网络延迟。

## 实体身份与生命周期

同步数据不能只带数组下标。至少需要：

```text
networkEntityId + generation/spawnVersion
```

客户端处理顺序：

1. 收到 Spawn，建立网络实体和初始基线；
2. 收到 Delta，只应用到匹配 generation 的实体；
3. 收到 Despawn，停止表现并清理历史；
4. 晚到的旧状态因 generation 不匹配被丢弃。

这能避免对象槽位复用后，旧网络包把新对象移动到错误位置。

## 同步边界

应该同步**游戏语义**，而不是盲目复制运行时对象：

- 同步 `movementMode = Falling`，不一定同步 Animator 当前 State 的内部索引；
- 同步技能 ID、阶段和起始 Tick，不必逐帧同步粒子；
- 同步逻辑位置/速度，不必同步摄像机抖动和纯本地 IK；
- 同步资源 ID，不发送裸指针、引擎对象地址或未版本化内存块。

# 游戏同步模型面试复习

## 先回答：游戏同步到底同步什么

网络游戏不是把每台机器的画面逐像素复制，而是让各端对**同一条游戏时间线上的关键事实**达成足够一致的认知。

最常见的三类模型：

| 模型 | 主要同步对象 | 谁推进核心模拟 | 常见体验手段 |
|---|---|---|---|
| 权威状态同步 | 状态结果、状态增量、离散事件 | 服务器 | 本地预测、快照插值、误差校正 |
| 确定性帧同步 | 按逻辑 Tick 排序的玩家输入/命令 | 各端运行同一套确定性模拟；服务器可同时运行 | 输入延迟、追帧、校验 Hash |
| Rollback | 输入帧；本地先预测缺失输入 | 各端确定性模拟并保存历史 | 预测远端输入、回滚、重模拟 |

现代项目通常是混合方案。例如角色移动用状态同步和本地预测，格斗战斗使用 Rollback，天气和任务用低频事件，服务器再周期性下发校验或恢复快照。

## 不要混淆的四个维度

```text
同步模型：复制状态，还是复制输入？
权威模型：服务器、房主，还是对等节点拥有最终裁决权？
网络拓扑：专服、Listen Server、Relay，还是 P2P？
传输语义：可靠/不可靠、有序/无序，基于 TCP、UDP、QUIC 或自研协议？
```

这些维度可以组合。帧同步可以有权威服务器；状态同步可以跑在 UDP 可靠层上；Rollback 既可以 P2P，也可以由服务器中继和验证。

## 统一分析模板

面对任意同步方案，按以下顺序回答：

1. **同步对象**：输入、命令、完整状态、增量状态还是事件？
2. **权威位置**：谁能修改最终状态，谁只负责表现？
3. **时间模型**：使用哪个 Tick，如何处理延迟、抖动、丢包和乱序？
4. **上行数据**：客户端发输入、视角、请求还是预测结果？
5. **下行数据**：服务器发快照、确认号、其他玩家输入、事件还是校验值？
6. **客户端表现**：本地预测、远端插值、外推、回滚还是直接等待？
7. **恢复方式**：误差如何校正，断线如何重连，分歧如何定位？
8. **安全边界**：服务器验证什么，客户端不应知道什么？
9. **适用场景**：实体规模、玩家数、交互精度、延迟预算和中途加入要求是什么？

## 方案对比

| 维度 | 状态同步 | 确定性帧同步 | Rollback |
|---|---|---|---|
| 网络主要传输 | 输入上行，快照/增量下行 | 各玩家输入帧 | 输入帧与确认 |
| 服务器计算 | 完整权威模拟 | 收集/排序/验证；可运行权威模拟 | 中继/验证；可运行权威模拟 |
| 客户端计算 | 预测自己、插值他人 | 完整模拟 | 完整预测模拟和重模拟 |
| 确定性要求 | 较低 | 很高 | 很高 |
| 下行带宽 | 随相关实体和状态量增长 | 通常随玩家输入量增长 | 通常随玩家输入量增长 |
| 延迟隐藏 | 预测、插值、外推 | 输入延迟或等待 | 预测缺失输入后回滚 |
| 中途加入 | 获取当前快照较直接 | 需要检查点 + 输入历史 | 需要检查点 + 输入历史 |
| 典型场景 | MMO、FPS、动作、开放世界 | RTS、棋类、部分 MOBA/战斗模拟 | 格斗、体育、少人数高精度对抗 |
| 主要风险 | 带宽、校正、服务器成本 | 非确定性、追帧、全量信息泄露 | 状态快照成本、副作用重放、回滚尖峰 |

场景只是常见选择，不是硬规则。FPS 也可能对部分系统使用输入复制，RTS 也可能由服务器下发状态。

## 30 秒回答

> 游戏同步的核心不是同步画面，而是同步能决定游戏结果的状态或输入。状态同步由服务器运行权威模拟并下发快照，客户端预测自己、插值他人；帧同步主要广播按 Tick 排序的输入，各端依靠确定性模拟得到相同结果；Rollback 同样同步输入，但会预测未到达的远端输入，真实输入晚到后恢复历史状态并重模拟。实际项目常按子系统混用，并通过 Tick、序列号、确认号、快照、校验 Hash、重连检查点和服务器验证保证一致性与安全。

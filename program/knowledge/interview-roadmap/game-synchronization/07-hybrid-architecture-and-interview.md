# 混合架构与面试设计题

## 为什么通常要混合

一个游戏内不同数据的性质不同：

| 数据 | 特征 | 常见方式 |
|---|---|---|
| 玩家移动 | 高频、可预测、服务器要验证 | 状态同步 + 本地预测 |
| 远端角色 | 高频、不能准确预测 | 状态快照 + 插值/有限外推 |
| 格斗核心 | 少人数、强交互、低延迟 | Rollback |
| RTS 单位 | 世界状态大、玩家命令少 | 确定性帧同步 |
| 背包/支付 | 低频、强一致 | 可靠请求/响应 + 服务器持久化 |
| 天气/任务阶段 | 低频全局状态 | 可靠事件或低频状态 |
| 粒子/音效 | 纯表现、可丢 | 本地派生或不可靠事件 |
| 中途加入 | 需要快速恢复 | 检查点/全量快照 + 增量 |

不要强迫所有系统共享一个频率、一种可靠性和一种权威策略。

## 选型问题

设计前依次问：

1. 最终结果必须由服务器裁决吗？
2. 玩家数、相关实体数和每实体状态量多大？
3. 玩家输入量与世界状态量哪个更小？
4. 能否保证跨平台确定性？
5. 本地操作可容忍多少延迟？
6. 是否使用复杂非确定性物理？
7. 是否支持中途加入、观战、回放和主机迁移？
8. 是否存在战争迷雾、隐藏牌或反作弊需求？
9. 服务器 CPU、带宽和部署成本预算多少？
10. 网络最差条件与目标地区是什么？

“动作游戏用状态同步、RTS 用帧同步”只是经验起点，不是设计证明。

## 场景参考

### MMO / 开放世界

- 服务器权威状态同步；
- AOI、优先级、Dormancy 和 Delta；
- 本地移动预测、远端插值；
- 技能请求由服务器验证；
- 中途加入直接获取区域快照；
- 纯表现事件可低可靠发送。

原因：动态实体多、玩家可随时加入、服务器必须隐藏和裁决大量状态，难以让所有客户端完整确定性模拟。

### FPS / TPS

- 玩家移动：输入上行 + 服务器权威 + Prediction/Reconciliation；
- 远端玩家：快照插值；
- Hitscan：服务器历史 Hitbox 回溯；
- 投射物：生成状态 + 客户端预测 + 命中确认；
- 装弹、弹药、伤害：可靠权威事件/状态；
- 高频姿态和视角：量化、不可靠更新。

### RTS

- 玩家发送低频命令；
- 服务器排序后广播逻辑 Tick 输入；
- 各端确定性模拟大量单位；
- 周期 Hash 和 Checkpoint；
- 掉线后检查点 + 输入日志追帧；
- 战争迷雾和全量信息需要额外安全设计。

### 格斗游戏

- 输入帧同步；
- 预测远端输入；
- 保存小型确定性状态；
- 真实输入晚到时 Rollback；
- 音效和特效按 Confirmed/Predicted 事件管理；
- 可使用 Relay 或权威服务器做验证与结算。

### 赛车 / 体育

可选两条路线：

- 服务器状态同步 + 车辆本地预测，适合复杂物理和较多玩家；
- 确定性模拟 + Rollback，适合状态较小、物理可控的强竞技。

选择取决于物理确定性、碰撞密度、玩家数和最大可接受回滚深度。

### 回合制 / 卡牌

- 可靠命令/事件；
- 服务器验证并生成权威状态；
- 不需要逐帧位置同步；
- 重点是幂等、版本、断线恢复和隐藏信息；
- “网络不实时”不代表不需要同步模型。

## 设计题示例：5v5 动作竞技

以下数字只用于说明回答结构，真实项目应以测试数据决定：

```text
Server Simulation：60 Tick/s
Input Send：30~60 Hz，冗余最近输入
State Snapshot：20 Hz，按 AOI 和优先级
Local Player：Prediction + Reconciliation
Remote Player：约 100 ms Snapshot Buffer
Hitscan：最多回溯 200 ms 的历史 Hitbox
Gameplay Event：Prediction Key 去重
Reconnect：区域 Keyframe + 增量事件
```

客户端上行：

- 输入序列、Tick；
- 移动轴、视角、按钮；
- 技能/开火 Prediction Key；
- 快照确认与网络统计。

服务器下行：

- Server Tick、Snapshot/Baseline Sequence；
- 已处理 Input Sequence；
- 相关实体的量化状态 Delta；
- Spawn/Despawn；
- 技能接受/拒绝、命中和伤害；
- 重连检查点和协议能力。

服务器验证移动、冷却、资源、射速和命中；客户端只预测表现。远端角色不按本地输入预测，而在历史快照间插值。

## 常见错误回答

| 错误表述 | 问题 |
|---|---|
| “帧同步就是同步每一帧画面” | 同步的是逻辑 Tick 输入 |
| “状态同步只同步位置” | 还包括生命周期、战斗状态、事件和确认 |
| “UDP 不可靠，所以不能做重要数据” | 可在 UDP 上实现选择性可靠通道 |
| “客户端预测就是客户端决定结果” | 预测只改善响应，服务器仍校正 |
| “Rollback 就是网络卡了倒退画面” | 恢复逻辑历史并重模拟，画面通常做平滑 |
| “帧同步不需要服务器计算” | 可有权威服务器同步运行和验证 |
| “使用 TCP 就不会乱” | 仍要处理业务版本、重复请求、断线和队头阻塞 |
| “服务器每帧下发所有 Transform” | 快照频率、AOI、Delta 和量化通常不同 |

## 2 分钟回答框架

```text
先给结论：同步的是状态结果还是输入原因
-> 权威在哪，客户端和服务器各模拟什么
-> 上行/下行的关键字段
-> 延迟通过预测、插值、输入延迟还是 Rollback 处理
-> 丢包、重连、校验和作弊如何处理
-> 为什么适合该游戏规模和交互特点
-> 用哪些指标验证
```

## 项目指标

面试中准备：

- 目标 Tick、输入/快照发送频率；
- 单玩家上下行 P50/P95；
- RTT/Jitter/Loss 测试档位；
- 平均/最大校正距离；
- Snapshot Buffer 欠载率；
- Rollback 频率和最大深度；
- AOI 内实体数量；
- Hash 分歧与重连耗时；
- 服务器每房间 CPU/内存。

没有做过线上项目时，也应说明如何用网络模拟器、录制输入、确定性回放和自动机器人验证。

## 最终自测

1. 为什么状态同步通常同步结果，帧同步同步原因？
2. 客户端预测后为什么仍需要服务器位置？
3. 远端玩家为何用插值而不是同样预测？
4. Rollback 怎样避免重复音效与伤害？
5. 状态同步和帧同步分别如何重连？
6. TCP/UDP 与同步模型为什么是正交关系？
7. 为 FPS、RTS、格斗和 MMO 各选方案，并说明反例条件。

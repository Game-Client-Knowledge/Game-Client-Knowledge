# 渲染基本概念

## 1. 渲染到底在做什么

实时渲染是把场景描述转换为二维图像，并且每秒重复许多次：

```text
场景中的几何、材质、灯光、摄像机
                |
                v
        一组颜色与深度计算
                |
                v
       屏幕上的二维像素网格
```

游戏世界并没有真的住在显示器里面。引擎保存的是位置、三角形、纹理、材质参数
等数据；渲染系统根据摄像机视角计算“哪些像素应该是什么颜色”。

屏幕是离散像素，场景在时间和空间上近似连续，因此渲染也包含采样问题：分辨率
太低会出现锯齿，帧率太低会出现不连续感，纹理采样不当会闪烁。这些现象不是
屏幕在闹情绪，而是采样频率和信号细节没有和平相处。

## 2. 一帧画面有哪些参与者

### 2.1 Mesh：形状数据

Mesh 通常包含：

- 顶点位置。
- 法线，用于描述表面朝向和光照。
- 纹理坐标 UV，用于在纹理上取样。
- 切线，用于法线贴图等切线空间计算。
- 顶点颜色、骨骼索引和权重等可选属性。
- 索引，用于复用顶点并组成三角形。

一个四边形通常由两个三角形组成：

```text
v3 -------- v2
| \         |
|   \       |
|     \     |
|       \   |
|         \ |
v0 -------- v1

索引示例：
三角形 A：v0, v1, v2
三角形 B：v0, v2, v3
```

GPU 最常处理三角形，因为三个不共线的点能确定一个平面，三角形始终是凸的，
并且内部属性可以稳定插值。四边形看起来更整齐，最终也常被拆成三角形上班。

### 2.2 Shader：计算规则

Shader 是运行在 GPU 特定阶段的小程序。最基础的两类是：

- **Vertex Shader**：逐顶点执行，主要计算变换后的位置和传给后续阶段的数据。
- **Fragment Shader**：逐片元执行，主要计算候选像素的颜色、深度等输出。

Shader 描述“怎么算”，不等于一件物体的完整材质配置。

### 2.3 Material：算法加参数

Material 通常引用某组 Shader，并保存该物体使用的参数与资源，例如：

```text
Shader：Lit
BaseColor：红色
Roughness：0.65
Metallic：0.0
BaseColorTexture：brick_albedo
NormalTexture：brick_normal
```

可以把 Shader 看成菜谱，Material 是“这次按菜谱使用哪些食材和口味参数”。
同一 Shader 可以服务许多 Material，同一 Mesh 也可以换不同 Material。

### 2.4 Texture 与 Sampler：数据和取样规则

Texture 是 GPU 可访问的图像或一般数据。它可以保存：

- 表面颜色。
- 法线、粗糙度、金属度。
- 阴影深度。
- 查找表、噪声、环境信息。
- 上一阶段渲染得到的结果。

Sampler 描述如何取样 Texture，例如：

- 最近点或线性过滤。
- 超出 UV 范围时重复、镜像或夹紧。
- 使用哪一级 Mipmap。
- 是否启用各向异性过滤。

纹理是地图，Sampler 是读地图的规则。两者相关，但不是同一个对象。

### 2.5 Camera：观察规则

摄像机决定：

- 位于哪里、朝向哪里。
- 使用透视投影还是正交投影。
- 可见视野范围。
- 近裁剪面和远裁剪面。
- 最终写到哪个 Render Target。

它不是场景里真的架了一台摄像机，而是一组从世界空间变到裁剪空间的参数。

### 2.6 Light：光照输入

灯光提供方向、位置、颜色、强度和范围等信息。它本身不会自动让物体变亮，
必须由 Shader 或预计算系统使用这些数据。

“场景里放了灯但模型还是黑的”经常意味着材质没有执行对应光照、法线错误、
曝光不合适，或者灯光根本没进入当前渲染路径。灯光并不享有强制照明权。

## 3. Buffer 与 Render Target

GPU 通过各种 Buffer 保存和传递数据：

| 名称 | 常见内容 |
|---|---|
| Vertex Buffer | 顶点位置、法线、UV 等 |
| Index Buffer | 顶点索引与三角形连接关系 |
| Constant/Uniform Buffer | 矩阵、灯光、材质参数 |
| Storage Buffer | 更通用的结构化读写数据 |
| Color Buffer | 每个像素的颜色 |
| Depth Buffer | 每个像素当前最近深度 |
| Stencil Buffer | 每个像素的小整数标记 |

Render Target 是渲染阶段写入的图像目标，可以是最终屏幕对应的颜色缓冲，也
可以是阴影图、后处理输入或离屏小地图。

Framebuffer 可以理解为当前一次渲染使用的一组附件组合，例如一个颜色附件、
一个深度附件和一个模板附件。不同图形 API 对具体对象和术语的组织略有差异，
面试时先讲概念职责，再说明 API 差异更稳妥。

## 4. Draw Call 是什么

Draw Call 是 CPU 通过图形 API 向 GPU 命令流提交一次绘制工作的常用称呼。
一次绘制通常需要提前绑定或指定：

```text
使用哪套管线状态和 Shader
-> 从哪些顶点/索引 Buffer 读取
-> 使用哪些纹理和参数
-> 写入哪个 Render Target
-> 绘制多少顶点、索引或实例
```

伪代码：

```cpp
bindPipeline(litPipeline);
bindMesh(cubeVertexBuffer, cubeIndexBuffer);
bindMaterial(redBrickMaterial);
setObjectMatrix(cubeTransform);
drawIndexed(36);
```

`drawIndexed(36)` 不是让 GPU 立刻在这一行完成绘制。命令通常先被记录、排队，
再由 GPU 异步执行。

Draw Call 的成本不只在 GPU 画了多少东西，也包括 CPU 准备命令、驱动验证、
状态切换和提交。因此“一百万个三角形一次画”与“一百万次各画一个三角形”
拥有相同三角形数量，却很可能完全不是同一种性能体验。

## 5. CPU 与 GPU 如何分工

### CPU 更擅长

- 游戏逻辑和复杂控制流。
- 场景遍历、粗粒度可见性判断。
- 资源和生命周期管理。
- 排序、批处理和命令构建。

### GPU 更擅长

- 对大量顶点或片元执行相似计算。
- 向量、矩阵和纹理采样。
- 高吞吐的并行任务。

两者通常异步流水：

```text
CPU：准备第 N+1 帧  [==========]
GPU：执行第 N 帧        [================]
显示：呈现第 N-1 帧                         [=]
```

异步能重叠工作，但也带来资源生命周期和同步问题。CPU 若必须立刻读取 GPU
结果，就可能等待 GPU 清空前面的任务；这类同步点会把并行流水线变回排队现场。

## 6. 帧时间比 FPS 更适合分析

两者关系是：

```text
FPS = 1000 / 单帧毫秒数
```

| 帧率 | 每帧预算 |
|---:|---:|
| 30 FPS | 约 33.33 ms |
| 60 FPS | 约 16.67 ms |
| 90 FPS | 约 11.11 ms |
| 120 FPS | 约 8.33 ms |

从 100 FPS 提升到 110 FPS 只节省约 0.91 ms；从 30 FPS 提升到 40 FPS 节省
约 8.33 ms。分析优化时看毫秒更直接，因为各阶段花费可以相加，FPS 不行。

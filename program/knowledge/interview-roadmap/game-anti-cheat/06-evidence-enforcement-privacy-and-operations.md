# 证据、处置、申诉、隐私与运营

## 防作弊闭环

```text
预防 -> 实时阻断 -> 风险信号
-> 聚合证据 -> 自动/人工复核
-> 分级处置 -> 申诉
-> 规则与模型回归
```

只有检测没有处置，作弊收益仍然存在；只有封禁没有证据和申诉，正常玩家会承担系统错误。

## 证据等级

| 等级 | 例子 | 适合动作 |
|---|---|---|
| 确定性不变量 | 无权限调用、资源不守恒、有效证明伪造 | 实时拒绝、记录、提高风险 |
| 多源高置信 | 权威行为异常 + 完整性异常 + 回放一致 | 自动限制或处罚 |
| 统计高风险 | 长期行为模型异常、关系图异常 | 隔离、增加采样、人工复核 |
| 单一弱信号 | Root、模拟器、一次超时、单次举报 | 不单独处罚，继续观察 |
| 无法复现 | 仅客户端视频或模糊举报 | 保留线索，不下确定结论 |

处罚强度应与证据强度、影响范围、历史记录和地区政策匹配。

## 实时阻断与延迟处置

### 实时阻断

适合：

- 非法状态转移；
- 重复领奖和越权交易；
- 超出协议长度/频率；
- 明确无权限操作；
- 会直接破坏经济或服务稳定性的请求。

目标是让作弊结果无法进入权威状态，而不是等对局结束后再封号。

### 延迟处置

适合：

- 自瞄、机器人和演员等统计判断；
- 需要隐藏检测规则；
- 需要聚合多局证据；
- 需要观察账号关联和资产流向。

延迟封禁可以增加作弊作者定位触发规则的难度，但不能为了“封禁波次”长期放任作弊伤害玩家。可先隔离匹配、取消排名收益或加强审计。

## 处置梯度

可能措施：

1. 请求拒绝或状态校正；
2. 警告与安全教育；
3. 移除异常收益、回滚结算；
4. 限制交易、排名、聊天或高价值模式；
5. 增加认证与人机验证；
6. 隔离匹配或风险队列；
7. 临时停权；
8. 永久封禁；
9. 关联账号/设备的风险控制；
10. 对组织化滥用采取法律和平台协作。

不透明的 Shadow Ban 可能降低对抗反馈，但涉及公平、消费者权益和申诉问题，应经过政策与法务评审。

## 证据链

处罚记录应能回答：

- 谁在何时、哪个版本、哪场对局触发？
- 原始权威事件和客户端风险信号是什么？
- 使用了哪个规则/模型版本？
- 风险分数和阈值来自哪个配置版本？
- 是否经过人工复核，复核者是谁？
- 执行了什么动作，影响哪些资产和比赛？
- 后续申诉和撤销过程是什么？

关键日志要防篡改、分级访问、设置保存周期，并能从 Match/Account/Device/Action ID 串联。

## 自动复核材料

可生成案件包：

```text
Case ID
+ Account / Match / Build / Rule Version
+ 权威输入与状态片段
+ 网络与设备上下文
+ 特征解释与相似历史
+ 举报和回放定位
+ 资产/关系图影响
```

面向审核员的工具要显示证据和上下文，不只显示一个“作弊概率 98%”。

## 误封与申诉

误伤来源：

- 新版本改变正常行为分布；
- 职业玩家或无障碍设备表现特殊；
- 网络抖动制造移动/输入异常；
- 安全软件、覆盖层和驱动冲突；
- 账号被盗后由攻击者作弊；
- 家庭、网吧或云游戏共享环境；
- 遥测丢失、时间错位或模型数据错误。

申诉流程需要：

1. 稳定 Case ID 和处罚理由类别；
2. 独立复核，不让原规则自动重复原结论；
3. 检查账号盗用与设备变化；
4. 可撤销处罚、恢复资产和排名；
5. 将撤销结果反馈到规则/模型；
6. 监控申诉耗时和撤销率；
7. 不向申诉者泄露足以绕过检测的细节。

## 灰度与 Kill Switch

新规则/模型上线：

```text
离线回放 -> Shadow Mode
-> 小流量告警 -> 仅限制低风险能力
-> 分地区/模式灰度 -> 正式处置
```

必须具备：

- 规则、特征和模型版本；
- 实时关闭或降权；
- 白名单和兼容性回滚；
- 对照组与误伤监控；
- 处罚前的最小样本量；
- 版本发布后的分布漂移告警。

客户端安全组件也要支持安全停用，避免驱动或兼容问题扩大为全量崩溃。

## 隐私与数据治理

防作弊数据可能涉及设备、进程、输入、位置、社交、支付和账号关系。需要：

- 明确目的、合法依据和玩家告知；
- 数据最小化，不采集与安全无关内容；
- 分地区配置采集与保存周期；
- 传输和存储加密；
- 原始标识与分析数据分离；
- 严格 RBAC、操作审计和导出控制；
- 第三方防作弊 SDK 供应链评估；
- 数据删除、账号注销和监管请求流程；
- 对未成年人和敏感地区额外评审。

高权限不等于无限访问。内核组件和进程扫描尤其需要明确边界。

## 安全组件自身安全

防作弊系统是高价值攻击目标：

- 客户端驱动漏洞可能变成本地提权；
- 更新渠道被劫持会影响全量玩家；
- 规则后台和白名单权限可被滥用；
- 内部案件数据可能泄露检测能力和玩家隐私；
- 自动处罚接口可能被错误调用。

措施：

- 最小权限、代码审计和漏洞响应；
- 发布签名与双人审批；
- 后台 RBAC、MFA 和操作审计；
- 敏感规则与原始数据分级；
- 自动处罚额度和速率限制；
- 第三方组件 SBOM、版本和 CVE 管理。

## 事故响应

### 作弊爆发

1. 确认影响模式、版本和资产；
2. 优先在服务器阻断收益；
3. 提高采样并保存证据；
4. 灰度规则或隔离匹配；
5. 修复客户端/服务器；
6. 回溯资产和比赛；
7. 公告、补偿和复盘。

### 误封爆发

1. 立即关闭规则或处罚动作；
2. 冻结批量处置队列；
3. 确定受影响版本和人群；
4. 自动撤销处罚和恢复权益；
5. 提供透明说明与快速申诉；
6. 补充回归数据和上线保护。

## 运营指标

| 指标 | 目标 |
|---|---|
| Prevented Invalid Actions | 有多少非法结果被实时阻止 |
| Cheater Exposure | 正常玩家遭遇作弊的对局比例 |
| Time to Detect / Contain | 发现和止损速度 |
| Precision / Recall | 检测质量 |
| Appeal Overturn Rate | 误封与申诉质量 |
| Repeat / Ban Evasion | 换号和复发情况 |
| Economic Recovery | 异常资产追缴比例 |
| Rule Kill-switch Time | 错误规则的止损速度 |
| Client Stability Impact | 安全组件对崩溃/性能的影响 |

封禁数量不是最终北极星指标。更重要的是正常玩家受到的作弊影响是否下降。

3. 处罚案件应保存哪些版本和原始证据？
4. 如何在不泄露检测细节的情况下支持申诉？
5. 新模型为什么要先跑 Shadow Mode？
6. 内核防作弊为什么也是供应链风险？

# 同步状态设计

## 1. 两种"同步的状态"

两套架构里"同步的状态"含义完全不同：

- **帧同步**：网络上同步的是**指令流**，游戏状态是"由确定性逻辑推导出来的
  派生数据"，本质不传状态，只有校验与恢复时才传。
- **状态同步**：网络上同步的是**世界状态本身**，指令只是客户端向服务器的
  单向上报。

## 2. 帧同步：指令流设计

### 2.1 指令结构

指令是帧同步网络包的基本单元。典型设计：

```cpp
struct Command {
    uint32 frame_no;    // 目标逻辑帧号（生效帧，不是发出时刻）
    uint8  player_id;   // 来源玩家
    uint8  op;          // 指令类型（移动 / 攻击 / 技能 / ...）
    uint32 param;       // 参数（目标坐标、技能 ID、目标实体等，位打包）
};

struct FrameCommand {             // 一个逻辑帧的完整输入集合
    uint32  frame_no;
    Command cmds[MAX_PLAYERS];    // 每个玩家一条，哪怕为空
};
```

设计要点：

- 每个玩家每帧必须有且只有一条指令（可以为空），保证"第 N 帧的输入集合"
  在每台机器上完全一致，这是确定性的地基。
- 参数要位打包：坐标量化、类型用枚举、长度用变长编码，流量可以压到每帧
  几十字节。
- 指令只在帧边界统一生效，指令携带"生效帧号"，避免网络乱序导致各端执行
  顺序不同。

### 2.2 逻辑帧设计

- **Tick Rate**：逻辑帧率固定（如 15 / 30 tick/s），与渲染帧率解耦，
  逻辑帧率就是"确定性时间轴"。
- **帧号对齐**：开局时所有客户端同步起始帧号，此后帧号单调递增。

### 2.3 输入延迟与帧缓冲

```text
客户端在渲染帧 100 产生输入
        | 附加到逻辑帧 100 + input_delay（如 2）上
服务器在逻辑帧 102 前把 FrameCommand 广播回来
        | 所有客户端（包括自己）在第 102 逻辑帧统一执行这条输入
```

- input_delay 越大越抗网络抖动，但手感越"重"；
- 网络波动时靠帧缓冲平滑：收到的 FrameCommand 先入队，逻辑线程按序消费；
- 缓冲空了就"等帧"（全体暂停等待下一帧指令），缓冲过多则"追帧"（逻辑
  加速推进，追上渲染帧率）。

### 2.4 确定性世界状态的约束

帧同步的状态虽然不传，但必须可被确定性推导、可哈希校验：

- **定点数替代浮点**：坐标、伤害用定点数或跨平台一致的整数运算，浮点舍入
  在不同 CPU 或编译器下可能不同，导致蝴蝶效应式分叉。
- **随机数统一**：禁止用时间做种子、禁止用语言库随机函数；使用自定义
  PRNG，种子开局同步；通常每个玩家各持一条独立随机流。
- **遍历顺序稳定**：实体表用数组或有序结构，禁止依赖哈希表遍历序。
- **同帧多指令执行顺序**：按玩家 ID 排序执行，或按指令类型分阶段
  （移动、攻击、结算），全部写入规范。

### 2.5 一致性校验与恢复

- **状态哈希**：每 N 帧（如 1000 帧）对世界状态算 checksum 上报服务器
  对比，发现分歧即可判定作弊或定位 bug。
- **快照 + 重放**：定期或断线重连时，由服务器或主机提供某个时间点的完整
  世界状态快照，客户端从该帧开始重放其后指令流追上进度。这是帧同步里
  仅有的"传状态"场景。

小结：帧同步的同步状态 = `FrameCommand` 指令流（主体）+ 状态哈希（校验）+
快照（恢复）。游戏状态本身是各端算出来的副本。

## 3. 状态同步：世界状态设计

### 3.1 状态建模与字段分类

服务器持有权威世界状态，通常按 ECS 建模。字段分三类：

| 类别 | 例子 | 同步方式 |
| --- | --- | --- |
| 持续状态 | 位置、朝向、血量、Buff | 状态复制（复制通道） |
| 瞬发事件 | 伤害跳字、技能特效触发、音效 | 事件消息（可靠 RPC 通道） |
| 纯本地展示 | 粒子、UI 动画 | 不同步 |

原则：**事实用状态，事件用消息**。状态复制保证"最终正确"，事件消息保证
"及时表现"。

### 3.2 快照与增量

```text
tick 0 ---- tick 1 ---- tick 2 ----
快照 S1       Δ            Δ         全量快照 S4 ...
```

- **快照**：某 tick 的完整复制状态集合，用于新客户端进场、断线重连、增量
  失步时的兜底。
- **增量**：相邻 tick 的 diff，服务器每 tick 只广播变化了的实体字段。
- **脏标记**：每个实体的每个复制字段带 dirty bit，本帧被修改才进入增量包。
- **可靠性分级**：位置这类高频状态用不可靠传输（丢一帧无所谓，下一帧会
  覆盖）；血量、掉落等用可靠或半可靠通道。

### 3.3 AOI 与复制策略

这是状态同步流量控制的核心——**AOI（Area of Interest，兴趣区域）**：

- **空间分区**：世界切成格子（九宫格或灯塔法）、四叉树或八叉树；
- 每个客户端订阅自己所在格子及其邻居格内的实体，视野外实体根本不进它的
  网络包（这也是防透视的根本手段）；
- 实体进出视野时发进入或离开通知（创建或销毁复制实体）。

配合优先级与带宽预算：

- 每 tick 设置字节预算（如 10KB），按优先级排序发送：战斗中的目标、近处
  单位、远处单位、背景对象；
- 远处实体降频（如 5 tick 更新一次位置）；
- 区分近处高频低延迟、远处低频高压缩。

### 3.4 压缩与量化

- **位置量化**：浮点坐标量化成厘米级整数，用 20 bit 表示一个轴
  （±500 米内 1cm 精度），比 64bit double 省 70% 以上；
- **朝向量化**：360 度压成 1 到 2 字节；
- **差分编码**：位置相对上一帧做增量编码，静止时几乎零字节；
- **血量只传百分比或枚举状态**，不传精确值，既省流量又防透视推导。

### 3.5 客户端时间补偿

客户端收到的是过去的状态，必须做时间补偿：

- **插值（Interpolation）**：保存最近 2 到 3 个快照，渲染落后服务器约
  `interp_delay`（如 100ms）的历史位置，画面平滑但增加观感延迟；
- **本地预测（Prediction）+ 和解（Reconciliation）**：本地玩家的操作立即
  本地执行（零延迟手感），当服务器状态到达时与本地预测比对，不一致就回滚
  到服务器状态并重放后续输入；
- **快照历史（延迟补偿）**：服务器保存最近 N 个 tick 的快照（如 1 秒），
  处理"我打中了一个已经移动的人"时回退到开枪时刻的服务器状态做命中判定，
  即 FPS 的 Lag Compensation。

### 3.6 断线重连

直接拉取最新全量快照即可，无需重演历史，这是状态同步相对帧同步重连简单
的原因。

## 4. 设计对照总表

| 设计维度 | 帧同步 | 状态同步 |
| --- | --- | --- |
| 同步主体 | 指令流（FrameCommand） | 世界状态（快照 / 增量） |
| 状态来源 | 各端确定性推导（副本） | 服务器权威计算 |
| 时间组织 | 逻辑帧 + 帧桶 + 输入延迟 | Tick 快照 + 增量 |
| 流量控制 | 指令位打包（极小） | AOI 裁剪 + 量化压缩 + 脏标记 |
| 客户端补偿 | 帧缓冲 / 追帧 | 插值 / 预测 / 回滚和解 |
| 一致性保障 | 状态哈希 + 快照重放 | 服务器权威天然一致 |
| 重连 | 快照 + 指令重放 | 最新快照 |
| 核心约束 | 确定性（定点数 / 随机数 / 遍历序） | 带宽与延迟的取舍 |

## 5. 落地检查清单

做帧同步前先问：

- 逻辑是否可全部用定点数或确定性整数实现？
- 随机数是否全局统一种子、独立随机流？
- 所有容器遍历序是否稳定？同帧多指令的执行顺序是否有规范？
- input_delay 与帧缓冲的数值是否按目标网络环境调过？
- 有没有设计状态哈希上报与断线重连快照？

做状态同步前先问：

- 哪些字段进复制通道、哪些走事件、哪些纯本地？是否有 dirty 标记？
- AOI 用哪种空间结构？进出视野的通知协议是否完整？
- 每 tick 带宽预算多少？优先级与降频策略是否落地？
- 位置与朝向的量化精度与压缩方案是否定好？
- 客户端插值延迟、预测与和解、服务器快照历史是否配套实现？

# 基本概念与对比

## 1. 两种同步架构

游戏联机中，多个客户端要在同一局游戏里看到一致的世界。按"网络上传什么"，
同步架构可以分成两类：

- **帧同步**：所有客户端只互相同步操作指令，各自本地执行同一套确定性逻辑，
  算出相同的结果。
- **状态同步**：服务器是唯一权威，服务器运算游戏逻辑，把世界状态同步给
  客户端，客户端只上报操作并展示结果。

核心区别是：**同步的是"输入"还是"结果"。**

## 2. 帧同步

### 2.1 核心思想

服务器（或主机）不计算游戏结果，只负责把玩家的操作（例如"玩家 1 在第 100
帧按了攻击键"）广播给所有人。每台机器用完全相同的代码、相同的输入序列、
相同的随机种子，按固定逻辑帧推进，因此各自算出的结果天然一致。

### 2.2 关键概念

- **确定性（Determinism）**：同样的输入一定得到同样的结果。浮点运算、容器
  遍历顺序、随机数都要严格统一，通常使用定点数、自定义随机数发生器。
- **逻辑帧与渲染帧分离**：逻辑按固定节奏（如每秒 15 帧）推进，渲染帧率各自
  独立；逻辑落后时通过"追帧"赶上。
- **先输入后执行**：本地操作也要打包成指令，等服务器广播回来后才真正执行，
  因此存在输入延迟，这是帧同步手感偏"重"的原因之一。

### 2.3 优缺点

| 优点 | 缺点 |
| --- | --- |
| 网络流量极小（只传指令） | 要求逻辑严格确定性，开发约束高 |
| 天然支持回放与观战（存指令流即可重演） | 一帧卡顿全员等待，观感差，需要锁帧或乐观处理 |
| 服务器压力小，易于支持大规模同屏单位 | 防作弊困难（客户端可算出全量数据） |
| 断线重连只需快速重演指令 | 难以加入中途进场的玩家 |

### 2.4 典型应用

MOBA（王者荣耀、英雄联盟）、RTS（星际争霸 2、帝国时代）、战棋等
**单位多、网络流量敏感**的游戏。

## 3. 状态同步

### 3.1 核心思想

服务器是唯一权威。服务器运算游戏逻辑，把世界状态（位置、血量、属性等）
同步给客户端，客户端只上报操作并展示结果。

### 3.2 工作方式

1. 客户端把操作发给服务器。
2. 服务器按自己的帧率跑逻辑，算出新状态。
3. 服务器把变化的状态（配合插值、快照、增量）推送给客户端。
4. 客户端做**插值（Interpolation）**与**预测（Prediction）**来掩盖网络延迟，
   让画面平滑。

### 3.3 优缺点

| 优点 | 缺点 |
| --- | --- |
| 客户端无需确定性，开发自由（可用浮点、物理引擎） | 网络流量大（要传状态快照或增量） |
| 反作弊容易，服务器裁决一切 | 服务器计算压力大，承载上限较低 |
| 天然支持中途加入、断线后取最新快照恢复 | 延迟敏感，需大量插值与预测技术（如回滚） |

### 3.4 典型应用

FPS、MMORPG、动作类网游（CS、原神、魔兽世界等），以及任意使用物理引擎
的游戏。

## 4. 对比总表

| 维度 | 帧同步 | 状态同步 |
| --- | --- | --- |
| 同步单元 | 输入指令 | 世界状态 |
| 计算位置 | 各客户端（确定性） | 服务器 |
| 网络流量 | 极小 | 大 |
| 服务器 CPU | 低 | 高 |
| 反作弊 | 难 | 相对容易 |
| 回放观战 | 天然支持 | 需额外录制 |
| 中途加入 | 难 | 容易 |
| 核心约束 | 确定性 | 带宽与延迟 |

## 5. 延伸问题

### 5.1 为什么 MOBA 普遍用帧同步

一波团战同屏可能有几十上百个单位，若用状态同步需要广播每个单位的数据，
流量爆炸；帧同步只传几十字节的指令即可。

### 5.2 为什么 FPS 几乎不用帧同步

物理模拟（子弹、碰撞）难以保证跨平台确定性，且 FPS 对响应速度要求极高，
帧同步的输入延迟无法接受。

### 5.3 现在有混合方案吗

有。例如"服务器帧同步"（服务器也跑逻辑帧做裁判）、状态同步加客户端预测
回滚（Rollback Netcode，格斗游戏常用）等，都是对两种思想的融合。

## 6. 阅读结论

- 帧同步把"计算"交给每台客户端，网络传的是**输入**；
- 状态同步把"计算"交给服务器，网络传的是**状态**；
- 真实项目几乎都落在两者之间的光谱上，混合才是常态。

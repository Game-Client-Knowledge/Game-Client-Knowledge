# 反作弊机制设计

## 1. 总原则：客户端不可信

> 凡是客户端计算的结果，都要假设可能被篡改。

两种同步方式的可信边界不同，所以反作弊的发力点完全不同：

- **帧同步**：逻辑在客户端跑，作弊者可以算出或修改一切，反作弊核心是
  "验证"和"信息隔离"。
- **状态同步**：逻辑在服务器跑，客户端只能改自己的输入和展示，反作弊核心
  是"权威校验 + 保护客户端环境"。

## 2. 帧同步的反作弊

帧同步最大的软肋：客户端本地拥有完整世界状态和逻辑代码，地图全亮、血量
透视、改伤害、改速度都能做到。防御思路如下。

### 2.1 服务器裁判

服务器也跑一份（或部分）确定性逻辑，充当裁判：

- **全量裁判**：服务器完整模拟整局游戏，把每个客户端上报的指令放进模拟里
  执行，可以验证一切，代价是承受同等计算量，基本退化成"服务器权威帧同步"。
- **轻量裁判**：服务器只模拟可验证的关键子系统，例如技能冷却是否满足、
  移动是否合法（速度上限、碰撞、穿墙）、经济与资源变化是否守恒。

这是目前商用帧同步游戏的标配：客户端全量演算用于画面，服务器跑一个
"验证版"逻辑专门抓异常。

### 2.2 输入合法性校验

服务器不信任结果，只审查输入流本身：

- **时序校验**：指令帧号是否单调、是否在合理窗口内，不能伪造"提前"输入。
- **频率与 APM 校验**：人类手速有上限，指令密度异常即疑似宏或脚本。
- **状态前置校验**：死亡、眩晕状态下发出的操作直接拒绝。
- **范围校验**：点击坐标、技能目标是否在合法距离内。

### 2.3 一致性校验与状态指纹

- 每个逻辑帧结束后，客户端把当前状态的**哈希值**上报服务器或玩家间互相对比；
- 某个客户端的状态哈希与其他玩家（及服务器裁判）不一致，说明逻辑被改或
  数据被篡改，直接标记或踢出；
- 服务器还可以不定期下发挑战，让客户端对自身代码段或关键数据算哈希回传，
  检测注入的修改。

### 2.4 信息隔离

- 视野裁剪：服务器只下发玩家当前可见区域的数据。代价是部分回到状态同步，
  因此常做折中——例如只对关键隐私数据（草丛、战争迷雾内的单位）做服务器
  仲裁，不把坐标下发给客户端。
- 很多"帧同步"手游实际是混合架构：逻辑帧同步 + 关键视野数据服务器裁剪。

### 2.5 客户端加固

- 代码混淆、加壳、反调试、反注入，防止外挂改内存、改 so/dll；
- 逻辑放服务器可验证的脚本虚拟机里执行。

客户端加固只能提高成本，不能杜绝，真正的防线必须是服务器验证。

### 2.6 行为分析与事后追查

- 服务器记录完整指令流，天然可回放，玩家举报后重演整局即可取证；
- 对 APM、胜率、操作分布做统计风控，异常账号进灰名单或隔离池。

## 3. 状态同步的反作弊

状态同步的服务器权威本身就是最强大的反作弊机制：血量、位置、金币、伤害
全在服务器手里，客户端改内存改的只是"自己看到的样子"。主要威胁变成：
机器人或 Aimbot（读屏幕或内存自动瞄准）、客户端环境作弊（读本地渲染数据
做透视）、协议层攻击（篡改、伪造、重放网络包）。

### 3.1 服务器权威校验

- **移动校验**：服务器按速度上限、加速度约束验证每次位置上报，瞬移或加速
  直接拉回，对 Speedhack 免疫。
- **能力校验**：冷却、蓝量、技能范围全部服务器裁决。
- **经济与物品校验**：掉落、交易、金币流水服务器记账，杜绝刷钱。
- **频率限制**：每个动作做服务器端节流，拦截自动连招脚本。

### 3.2 协议安全

- **加密**：TLS 或自定义加密防止中间人篡改。
- **防重放**：带时间戳、nonce、序列号，防止复制旧包重放。
- **签名与密钥轮换**：客户端密钥易被提取，协议加密只能防"路人"，防不了
  逆向高手，依然只是门槛。

### 3.3 客户端环境保护

状态同步作弊（透视、自瞄）往往要读客户端内存里的画面数据或注入进程，
因此保护客户端环境很重要：

- **内核级反作弊组件**：如 EAC、BattlEye、腾讯 ACE、Vanguard，反注入、
  扫内存特征、检测调试器、验证驱动签名。
- **完整性校验**：登录时对游戏文件、内存关键区域做哈希验证。
- **硬件封禁**：设备指纹（HWID）提高作弊成本。

### 3.4 服务器端行为检测

- **瞄准行为统计**：准星移动角速度分布、瞄准反应时间（人类大于 150ms）、
  爆头率、击杀曲线，与人类基线比对。
- **输入熵检测**：真人鼠标轨迹有噪声，脚本轨迹过"干净"。
- **外挂特征库与机器学习风控**：基于海量对局数据训练异常检测模型。

### 3.5 信息最小化

- 服务器只下发视野内单位，墙后敌人根本不进网络包，这是防透视最有效的
  手段，代价是流量，因此 FPS 常用"可见性裁剪 + 延迟显示"策略。
- 降低客户端可推导信息：例如敌方血量只传百分比或枚举状态，直到击杀结算。

### 3.6 运营层

- **影子封禁**：让作弊者只匹配作弊者。
- **延迟封禁**：收集证据后批量封，避免外挂作者快速迭代绕过。
- **举报复核**：结合服务器端对局录像回放核实。

## 4. 对比总结表

| 维度 | 帧同步 | 状态同步 |
| --- | --- | --- |
| 最严重风险 | 改内存直接改结果（改伤、改钱、全图挂） | 透视、自瞄、自动化脚本 |
| 第一道防线 | 服务器裁判 + 输入合法性校验 | 服务器权威校验（天然） |
| 流量作弊 | 伪造或篡改指令流，需协议加密加时序校验 | 篡改上报包，由服务器校验兜底 |
| 透视类 | 客户端本就有全量数据，极难防，需视野裁剪 | 信息最小化下发可根治 |
| 天然优势 | 指令流即回放，事后追查容易 | 服务器裁决，数值类作弊基本免疫 |
| 客户端加固定位 | 辅助 | 重要（保护进程环境防注入读取） |

## 5. 落地优先级建议

1. **永远先做服务器验证**：帧同步做裁判、状态同步做全量权威校验，这是地基。
2. **信息最小化**（视野裁剪）是防透视的根本手段，客户端加固只是辅助。
3. **协议层**做加密、防重放、频率限制，挡住 80% 的脚本小子。
4. **客户端内核反作弊、行为风控、影子封禁**，对付剩下 20% 的专业选手。
5. 帧同步项目额外保留**完整指令流与状态哈希**，给举报审核和事后封号留证据。
